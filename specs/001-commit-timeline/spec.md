# Feature Specification: Cistory - GitHub Commit Timeline

**Feature Branch**: `001-commit-timeline`
**Created**: 2026-01-26
**Status**: Draft
**Input**: GitHub 커밋 히스토리 타임라인 웹서비스 "Cistory" - 일정 시간마다 GitHub 커밋 히스토리를 가져와서 타임라인으로 보여주고, AI가 기술자/비기술자 관점에서 요약해주는 웹사이트

## Scope & Constraints

### 서비스 대상
- **개인 도구**: 본 서비스는 개인 사용자가 자신의 GitHub 활동을 추적하고 요약하기 위한 개인용 도구이다
- 다중 사용자 공유, 팀 협업 기능은 현재 범위에 포함되지 않음
- 단일 사용자의 GitHub 계정 연동만 지원

### 타임라인 뷰 원칙
- **통합 타임라인**: 모든 추적 중인 레포지토리의 커밋을 하나의 타임라인에 시간순으로 통합하여 표시
- 레포지토리별 분리 뷰가 아닌, 전체 활동을 한눈에 볼 수 있는 통합 뷰가 기본
- 필터링을 통해 특정 레포지토리만 선택적으로 볼 수 있음

### 아키텍처 원칙
- **모듈화**: 각 기능은 독립적인 모듈로 분리되어야 하며, 모듈 간 의존성을 최소화해야 한다
- **추상화**: 외부 서비스(GitHub API, AI API, 데이터베이스) 연동은 추상화 계층을 통해 구현하여, 향후 다른 서비스로 교체 가능해야 한다
- **확장성**: 추후 기능 확장(팀 기능, 다른 VCS 지원, 다른 AI 모델 등)을 고려한 설계가 필요하다
- **단일 책임 원칙**: 각 컴포넌트/모듈은 하나의 명확한 책임만 가져야 한다

### 테스트 범위
- **자동화 테스트 제외**: 단위 테스트, 통합 테스트, E2E 테스트 등 자동화된 테스트 코드는 작성하지 않음
- **수동 테스트**: 사용자가 직접 기능을 검증함
- 기능 규모가 작고 개인 도구이므로 테스트 자동화 오버헤드 불필요

## User Scenarios & Testing *(mandatory)*

### User Story 1 - GitHub 계정 연동 및 레포지토리 선택 (Priority: P1)

사용자가 자신의 GitHub 계정을 연동하고, 타임라인에 표시할 레포지토리를 선택한다. 선택한 레포지토리의 커밋 히스토리가 자동으로 동기화되어 타임라인에 표시된다.

**Why this priority**: 서비스의 핵심 기반이 되는 기능. GitHub 연동 없이는 어떤 기능도 동작하지 않음.

**Independent Test**: GitHub 계정 연동 후 레포지토리 목록을 확인하고, 선택한 레포지토리의 커밋이 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 로그인하지 않은 상태, **When** "GitHub으로 연동하기" 버튼 클릭, **Then** GitHub OAuth 인증 화면으로 이동하고, 인증 완료 후 서비스로 돌아와 연동된 상태가 표시됨
2. **Given** GitHub 연동이 완료된 상태, **When** 레포지토리 목록 페이지 접근, **Then** 사용자의 모든 접근 가능한 레포지토리 목록이 표시됨
3. **Given** 레포지토리 목록이 표시된 상태, **When** 특정 레포지토리 선택, **Then** 해당 레포지토리가 추적 대상에 추가되고 커밋 동기화가 시작됨
4. **Given** 연동된 상태, **When** 연동 해제 요청, **Then** 모든 연동 데이터가 삭제되고 미연동 상태로 돌아감

---

### User Story 2 - 커밋 타임라인 조회 (Priority: P1)

사용자가 선택한 레포지토리의 커밋 히스토리를 수직 타임라인 형태로 조회한다. 최신 커밋이 상단에 표시되며, 각 커밋의 기본 정보와 AI 요약이 함께 표시된다.

**Why this priority**: 서비스의 핵심 가치 제공. 사용자가 실제로 보는 메인 화면.

**Independent Test**: 동기화된 레포지토리를 선택하고 타임라인에 커밋들이 시간순으로 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 커밋이 동기화된 레포지토리가 있는 상태, **When** 타임라인 페이지 접근, **Then** 모든 레포지토리의 커밋이 하나의 통합 타임라인에 최신순으로 표시됨
2. **Given** 타임라인이 표시된 상태, **When** 스크롤 다운, **Then** 추가 커밋이 로드되어 표시됨 (무한 스크롤 또는 페이지네이션)
3. **Given** 타임라인이 표시된 상태, **When** 레포지토리 필터 선택, **Then** 선택한 레포지토리의 커밋만 필터링되어 표시됨
4. **Given** 타임라인이 표시된 상태, **When** 날짜 범위 필터 설정, **Then** 해당 기간 내 커밋만 필터링되어 표시됨

---

### User Story 3 - AI 요약 조회 (기술자/비기술자 관점) (Priority: P1)

사용자가 각 커밋에 대해 기술자 관점과 비기술자 관점의 AI 요약을 조회한다. 기술자 요약은 코드 변경 내용을, 비기술자 요약은 기능적 변화를 설명한다.

**Why this priority**: 서비스의 차별화된 핵심 가치. 단순 커밋 로그가 아닌 의미 있는 요약 제공.

**Independent Test**: 커밋 상세 화면에서 두 가지 관점의 요약이 각각 표시되고, 토글로 전환 가능한지 확인.

**Acceptance Scenarios**:

1. **Given** 타임라인에 커밋이 표시된 상태, **When** 특정 커밋 카드 확장, **Then** 기본적으로 비기술자 관점 요약이 표시됨
2. **Given** 비기술자 요약이 표시된 상태, **When** "기술자 관점" 토글 선택, **Then** 기술적 상세 요약으로 전환됨
3. **Given** 요약이 아직 생성되지 않은 커밋, **When** 커밋 카드 확장, **Then** "AI 요약 생성 중..." 상태가 표시되고, 완료 후 요약이 표시됨
4. **Given** 요약이 생성된 상태, **When** 요약 내용 확인, **Then** 비기술자 요약은 "이런 기능이 추가/수정되었습니다" 형태로, 기술자 요약은 "어떤 파일의 어떤 부분이 왜 변경되었는지" 형태로 표시됨

---

### User Story 4 - 실시간 동기화 및 상태 표시 (Priority: P2)

시스템이 주기적으로 GitHub에서 새 커밋을 가져오고, 사용자에게 동기화 진행 상태를 실시간으로 표시한다.

**Why this priority**: 데이터 최신성 보장 및 사용자 경험 향상. P1 기능들이 동작한 후 필요.

**Independent Test**: 동기화 실행 시 진행 상태 메시지가 순차적으로 표시되고, 완료 후 새 커밋이 타임라인에 추가되는지 확인.

**Acceptance Scenarios**:

1. **Given** 추적 중인 레포지토리가 있는 상태, **When** 수동 동기화 버튼 클릭, **Then** "깃허브에서 커밋 히스토리 가져오는 중..." 상태 표시됨
2. **Given** 커밋 가져오기 완료 후, **When** 새 커밋이 있는 경우, **Then** "AI 요약 생성 중... (3/5)" 형태로 진행률 표시됨
3. **Given** 모든 처리 완료 후, **When** 타임라인 확인, **Then** 새로운 커밋이 상단에 추가되어 있음
4. **Given** 자동 동기화 설정이 활성화된 상태, **When** 설정된 주기(기본 1시간)가 경과, **Then** 백그라운드에서 자동으로 동기화 수행

---

### User Story 5 - 다크모드 및 모바일 반응형 (Priority: P2)

사용자가 다크모드와 라이트모드를 전환하고, 모바일 기기에서도 최적화된 UI로 서비스를 이용한다.

**Why this priority**: 사용자 경험 향상. 핵심 기능 완성 후 폴리싱 단계.

**Independent Test**: 테마 토글 시 즉시 UI가 전환되고, 모바일 화면에서 타임라인이 적절히 표시되는지 확인.

**Acceptance Scenarios**:

1. **Given** 라이트모드 상태, **When** 다크모드 토글 클릭, **Then** 즉시 다크모드 UI로 전환됨
2. **Given** 다크모드 상태에서 재접속, **When** 페이지 로드, **Then** 이전에 선택한 다크모드 상태가 유지됨
3. **Given** 데스크탑 브라우저에서 접속, **When** 화면 너비를 768px 이하로 조정, **Then** 모바일 최적화 레이아웃으로 변경됨
4. **Given** 모바일 기기에서 접속, **When** 타임라인 조회, **Then** 터치 친화적인 UI와 적절한 폰트 크기로 표시됨

---

### Edge Cases

- **연동된 레포지토리가 삭제된 경우**: 다음 동기화 시 "레포지토리를 찾을 수 없음" 알림 표시, 해당 레포지토리 비활성화 처리
- **GitHub API 속도 제한에 도달한 경우**: "잠시 후 다시 시도해주세요" 메시지 표시, 제한 해제 시간 안내
- **매우 큰 레포지토리(커밋 수 10,000개 이상)의 경우**: 최근 6개월 또는 1,000개 커밋만 초기 동기화, 이전 커밋은 요청 시 로드
- **커밋에 변경 파일이 없는 경우(예: 머지 커밋)**: "머지 커밋입니다" 표시, 머지된 브랜치 정보 제공
- **AI 요약 생성 실패 시**: "요약 생성 실패 - 다시 시도" 버튼 표시, 3회 실패 시 수동 재요청만 가능
- **네트워크 연결 끊김 시**: 오프라인 상태 표시, 캐시된 데이터로 타임라인 표시, 연결 복구 시 자동 동기화
- **다중 브랜치 커밋이 있는 경우**: 기본적으로 default 브랜치(main/master) 커밋만 표시, 필터로 다른 브랜치 선택 가능

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 GitHub OAuth를 통해 사용자 인증을 수행해야 한다
- **FR-002**: 시스템은 인증된 사용자의 접근 가능한 레포지토리 목록을 조회해야 한다
- **FR-003**: 사용자는 타임라인에 표시할 레포지토리를 선택/해제할 수 있어야 한다
- **FR-004**: 시스템은 선택된 레포지토리의 커밋 히스토리를 가져와 저장해야 한다
- **FR-005**: 시스템은 모든 추적 레포지토리의 커밋을 하나의 통합 타임라인에 최신순으로 정렬하여 수직 형태로 표시해야 한다
- **FR-006**: 각 커밋 카드에는 커밋 메시지, 작성자, 날짜, 변경 파일 수가 표시되어야 한다
- **FR-007**: 시스템은 각 커밋에 대해 AI 기반 요약을 생성해야 한다
- **FR-008**: AI 요약은 기술자 관점(코드 변경 상세)과 비기술자 관점(기능 변화)으로 구분되어야 한다
- **FR-009**: 비기술자 요약은 "어떤 기능이 추가/수정되었는지"를 일반인도 이해할 수 있는 언어로 설명해야 한다
- **FR-010**: 기술자 요약은 "어떤 파일의 어떤 부분이 왜 변경되었는지"를 포함해야 한다
- **FR-011**: 시스템은 설정된 주기(기본 1시간)마다 자동으로 새 커밋을 동기화해야 한다
- **FR-012**: 사용자는 수동으로 즉시 동기화를 트리거할 수 있어야 한다
- **FR-013**: 동기화 중 진행 상태를 실시간으로 표시해야 한다
- **FR-014**: 사용자는 레포지토리별, 날짜 범위별로 타임라인을 필터링할 수 있어야 한다
- **FR-015**: 시스템은 다크모드와 라이트모드를 지원하고, 사용자 선택을 저장해야 한다
- **FR-016**: 시스템은 모바일 기기에서 최적화된 반응형 UI를 제공해야 한다
- **FR-017**: 사용자는 GitHub 연동을 해제하고 모든 관련 데이터를 삭제할 수 있어야 한다

### Non-Functional Requirements (Architecture)

- **NFR-001**: 시스템은 모듈화된 구조로 설계되어, 각 기능(인증, 동기화, 요약 생성, UI)이 독립적으로 개발/테스트/배포 가능해야 한다
- **NFR-002**: 외부 서비스 연동(GitHub API, AI API, 데이터베이스)은 인터페이스/어댑터 패턴으로 추상화하여, 구현체 교체 시 비즈니스 로직 변경이 불필요해야 한다
- **NFR-003**: 향후 다른 VCS(GitLab, Bitbucket 등) 지원을 위해 VCS 연동 계층이 확장 가능해야 한다
- **NFR-004**: 향후 다른 AI 모델(GPT, Gemini 등) 지원을 위해 AI 요약 계층이 확장 가능해야 한다
- **NFR-005**: 각 모듈/컴포넌트는 단일 책임 원칙을 준수하여, 하나의 변경 사유만 가져야 한다

### Key Entities

- **User**: 서비스 사용자. GitHub 계정과 연동되며, 선택한 레포지토리 목록과 테마 설정을 보유
- **Repository**: 추적 중인 GitHub 레포지토리. 사용자와 연결되며, 동기화 상태와 마지막 동기화 시간 정보 보유
- **Commit**: 개별 커밋 정보. 레포지토리에 속하며, 커밋 메시지, SHA, 작성자, 날짜, 변경 파일 목록 보유
- **CommitSummary**: 커밋에 대한 AI 생성 요약. 기술자 요약과 비기술자 요약을 각각 저장
- **SyncJob**: 동기화 작업 정보. 시작 시간, 상태, 진행률, 완료 시간 추적

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 GitHub 연동부터 첫 타임라인 조회까지 3분 이내에 완료할 수 있다
- **SC-002**: 타임라인 페이지 초기 로딩이 3초 이내에 완료된다
- **SC-003**: AI 요약 생성이 커밋당 평균 10초 이내에 완료된다
- **SC-004**: 비기술자 요약을 읽은 사용자의 80% 이상이 해당 커밋의 의미를 이해할 수 있다 (사용자 피드백 기반)
- **SC-005**: 모바일 기기에서 모든 핵심 기능(타임라인 조회, 필터링, 요약 확인)이 정상 동작한다
- **SC-006**: 시스템이 100개의 동시 사용자를 성능 저하 없이 처리할 수 있다
- **SC-007**: 동기화 진행 상태가 2초 이내 간격으로 업데이트된다

## Assumptions

- 사용자는 GitHub 계정을 보유하고 있다
- 레포지토리당 최대 10,000개 커밋까지 초기 동기화 지원, 이후 증분 동기화
- AI 요약은 커밋 diff와 커밋 메시지를 기반으로 생성한다
- 레포지토리의 README나 기존 문서를 참고하여 컨텍스트 기반 요약을 생성한다
- 동기화 주기는 사용자가 1시간~24시간 범위에서 설정 가능하다 (기본값: 1시간)
- Private 레포지토리 접근을 위해 적절한 GitHub OAuth scope를 요청한다
