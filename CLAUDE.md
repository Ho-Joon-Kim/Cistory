# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Cistory is a personal life-logging application that aggregates several private data streams into one dashboard: GitHub commits with AI-powered summaries, location via OwnTracks (visit/track/transport-mode/trip/subway detection), coding activity via WakaTime (OAuth), Toss financial transactions via MacroDroid push notifications (with AI expense categorization), brokerage portfolio data via the Korea Investment & Securities (KIS) API, body composition via Withings, and health/fitness (steps, heart rate, sleep, workouts) via the Google Health API (Fitbit) plus an on-device Health Connect importer, and optional Proton Drive Photos (photo metadata, location and thumbnails, plus GPS/heading/UTC offset read once from each original's EXIF, with local NSFW pre-blocking; collection layer only, no photo UI yet). Built with Next.js 16, Better Auth (GitHub OAuth), Drizzle ORM with PostgreSQL (PostGIS), and the Anthropic SDK. The reporting surface is a single `/overview` dashboard over precomputed period snapshots with AI narratives (it replaced the separate `/insights` and `/report` pages), plus a `/travel` trip browser, a cross-source `/search`, a `/data-status` collection-status/recovery page, map visualization (Mapbox/Kakao), OSM subway data via Overpass, and background sync via node-cron (dedicated container in production, in-process during dev), with Sentry error tracking and Better Stack structured logging.

Tests are colocated `*.test.ts` files (e.g. `src/lib/cron.test.ts`, `src/modules/transaction/parser.test.ts`). The `include` glob covers **`scripts/**` as well as `src/**`**, so the eight `scripts/*.test.ts` files run under `yarn test` too. `vitest.config.mts` injects fake `DATABASE_URL`/auth/API-key env vars before test modules load — `src/lib/auth.ts` constructs a `pg.Pool` at module scope and most route modules transitively import it, but pool construction opens no connection, so no real DB is needed. Vitest is **v5**: `vite` must stay an explicit devDependency (it is a peer dep that Yarn won't install), `clearMocks` defaults to `true` (every mock's call history is cleared before each test, on top of the `vi.restoreAllMocks()` in `vitest.setup.ts` — so never assert on calls made in another test, a `beforeAll`, or at module top level), unawaited `.resolves`/`.rejects` assertions fail the test, and `vi.mock`/`vi.hoisted` must be top-level. `src/app/api/_routes-import.test.ts` is a glob-driven smoke test asserting every `src/app/api/**/route.ts` imports cleanly and exports at least one HTTP verb — it catches import-time crashes across all routes at once.

**Integration tests are a separate, opt-in suite that does need a database.** Colocated `*.integration.test.ts` files (27 files: `src/db/sql`, `subway-match/usage`, `search/service`, `summary/service` (atomic claims), `data-status/{service,telemetry}`, `lib/account-deletion`, `lib/auth-compatibility` (real signed Better Auth cookies against the legacy schema), `spending/classify` (`bucketSql` mirror/cancel correlation), `transaction/reparse-service`, plus health (`health-user-id`, `webhook-queue`), overview (`aggregate/coding`, `narrative`, `history-store`, `precompute`/`service` claim order and stale snapshots), `location/services/saved-place-address`, `spending/{service,refund}`, and the seven `modules/proton/*` files (`backfill`, `cascade`, `events`, `ingest`, `location`, `originals`, `summary`: location-fill settle rules and the UTC assumption, cascade delete, cursor transactions, the NSFW block path)) run under `vitest.integration.config.mts` against a disposable PostGIS Postgres, and execute real SQL — the properties they pin (session-timezone behavior, join direction, cross-user row isolation) are facts about Postgres, not about TypeScript, so no mock or unit test can establish them. `vitest.config.mts` explicitly excludes `*.integration.test.ts` (it would otherwise match the unit glob too, since it ends in `.test.ts`), so `yarn test` never opens a connection and stays fast and DB-free.

`yarn test:integration` does the whole cycle: `docker compose -f docker-compose.test.yml up -d --wait` (an ephemeral, tmpfs-backed container — its own compose project, network, and port `5433`, never `cistory-db`), applies the real Drizzle migrations via `scripts/migrate.ts` against it (exercising the same migration path production uses, not a `drizzle-kit push` shortcut that could drift from the SQL actually shipped), then runs the suite. `yarn db:test:down` removes it; leaving it up between runs is fine and faster for iteration since `yarn test:integration` re-migrates idempotently on every invocation. **`docker-compose.test.yml` sets `TZ: Asia/Seoul` on the container, matching `docker-compose.yml`'s production `postgres` service exactly, and this is not cosmetic** — Postgres bakes the container's OS timezone into `postgresql.conf` as the session-default `TimeZone` GUC, and that default is the entire reason a bare `now()` in raw SQL yields KST wall time in production while everything Drizzle writes stays UTC wall time (the **Timestamps in SQL** bullets under Code Style below are the only written record of this — `src/db/sql.ts`'s header covers the UTC convention but never mentions `now()`). A test database left on UTC would make the integration suite pass while the real nine-hour trap it exists to catch stayed uncaught.

Isolation is transaction-per-test (`src/db/testing/transactional-db.ts`): each test file opens one dedicated `pg.Client`, wraps every test in `BEGIN`/`ROLLBACK`, and never commits — so tests never leak state into each other regardless of execution order, without per-table cleanup code to keep in sync as tables are added. This suite is intentionally targeted — each file pins a Postgres-level property (timezone, tenant isolation, lease/claim races, cascade/rollback) that a mock can't — rather than a blanket integration layer over the ~50 files in `src/` that build raw SQL; extend it by adding another focused `*.integration.test.ts` file, not by broadening existing ones. Use only a disposable database for `TEST_DATABASE_URL`.

**Browser tests** (`tests/browser/*.spec.ts`, `playwright.config.ts`) run against `scripts/browser-server.mjs`, which copies `src/` + config into a temp dir (never `.env*`), symlinks `node_modules`, swaps `output: "standalone"` off, injects `tests/browser/chart-page.tsx` as a `/browser-charts` gallery (only in the copy, never shipped), and starts with dummy auth, an unreachable loopback DB and `DISABLE_CRON=true`. Every API call is a fixture and external requests are blocked. They cover chart geometry (the hand-built `/spending` month bars and forecast curve, plus the four recharts components in the `/browser-charts` gallery), mobile width, KST date links from a non-KST browser, search, data-status recovery flows, and SSR/hydration ordering. When adding files that the app needs at boot (like `instrumentation-client.ts`), add them to the browser-server copy list too. Artifacts land in gitignored `test-results/` and `playwright-report/`.

Package manager is **Yarn 4.5.0** (Berry, via Corepack, node-modules linker). Use `yarn` for all package operations. Node is pinned to **24.22.2** in `.node-version` (also `engines`, Docker); `yarn dev`/`yarn build` call `scripts/check-node-version.mjs` explicitly and exit if the running Node is older or a different major — Yarn 4 doesn't run implicit `predev`/`prebuild` hooks, so that guard must stay inline in the script.

### Key Patterns

**API Route Authentication**: Four layered helper modules cover the common shapes:

- `src/lib/auth-helpers.ts` — `getAuthenticatedUser(request)` for session check, `getGitHubToken(userId)` for reading the GitHub OAuth token (sourced from Better Auth's `account` table — the old `users.github_access_token` column was dropped in migration 0017).
- `src/lib/api-handler.ts` — `withAuth` / `withValidation` wrappers that bundle session check + Zod body parse + structured error responses. Prefer these for new session-based routes. Throw `ApiError(status, message, code)` inside a handler to surface a structured error.
- `src/lib/api-key-route.ts` — `createApiKeyRoute({ column, prefix, label })` factory for the POST/DELETE pair that generates or revokes a prefixed API key on `users`. Used by OwnTracks, Toss, and health-import key routes. WakaTime is no longer an API-key integration (see Third-party OAuth below); `/api/settings/wakatime-key` survives only to answer `POST` with 410 and to clear a leftover legacy key.
- `src/lib/api-auth.ts` — hardening for public ingestion endpoints reachable by API key (OwnTracks, Toss, health-import). Exposes `verifyApiKey()` (DB probe + `timingSafeEqual`), `enforceRateLimit()` (in-memory 60 req / 60s per key+IP), `checkBodySize()`/`bodyExceedsLimit()` (10 KB default cap), `checkSameOrigin()`, and `logIngestionFailure()`. All ingestion routes must pass the request through these before touching DB state. `/api/health-import` deliberately raises its own cap to 2 MB because it is a batched push of the user's own history.

```typescript
// Auth-only routes
const { user, error } = await getAuthenticatedUser(request);
if (error) return error;

// Or wrapper-style
export const GET = withAuth(async ({ user, request }) => { ... });
export const POST = withValidation(Body, async ({ user, body }) => { ... });

// GitHub-backed routes
const accessToken = await getGitHubToken(user.id);
```

**Third-party OAuth (Withings, Google Health, WakaTime)**: all three providers use the shared stateless `state` codec in `src/lib/oauth-state.ts` (wrapped per provider by `withings-oauth-state.ts` / `google-oauth-state.ts`). State is an HMAC-SHA256-signed `userId + nonce + expiry` (10 min TTL) with the key derived from `KIS_ENCRYPTION_KEY` plus a **distinct per-provider context string** — one provider's state must never verify against another's callback. That isolation is a security invariant covered by cross-verify tests; keep the contexts unique when adding a provider. Access/refresh tokens are AES-256-GCM encrypted via `src/lib/crypto.ts`. Google refresh tokens do **not** rotate, so a refresh response that omits one must preserve the stored token; Withings rotates them. All connections flip `status` to `needs_reauth` only on a *confirmed* auth failure so transient errors don't force re-linking.

**WakaTime** (`wakatime_connections`, `src/modules/wakatime/connection.ts`, routes `/api/wakatime/{authorize,callback}` + `DELETE /api/wakatime`): WakaTime made API keys write-only ("API keys are write-only and should only be used in WakaTime plugins") and reads with `Basic <api key>` now fail with 403 "API Keys are only for plugins, use your personal oauth token" — that is what stopped WakaTime sync in 2026-09. Reads now use `Authorization: Bearer <access token>`, scopes `read_summaries,read_heartbeats` (summaries / durations; we never call `/users/current`, which needs `email`). Code-flow tokens "expire after 100 years", so a missing expiry counts as fresh and refresh is mostly reactive (a 401 forces one refresh + retry). The docs don't say whether refresh rotates the refresh token, so a returned one replaces the stored one and an omitted one is kept. The token endpoint requires `redirect_uri` on every grant, so cron refreshes rebuild it from `NEXT_PUBLIC_APP_URL`. `needs_reauth` is set only on `invalid_grant` from the token endpoint or a 401 from a freshly refreshed token — never on 403/5xx/network. `users.wakatime_api_key` is **deprecated**: kept as a column, never used for API calls; when set without an OAuth connection the settings card and `/data-status` show a reconnect prompt, and connecting clears it. Sync, manual sync and `/data-status` recovery all go through `createWakaTimeSyncServiceForUser()`, which returns null without an *active* connection; the watermark stays on `users.wakatime_last_synced_at` and `trackSourceSync` telemetry is unchanged.

**Adapter Pattern**: `lib/adapters/` groups external-service clients. Geocoding, overpass, google-health, withings, and kis expose an `interface.ts`; ai, vcs, wakatime, and map-matching intentionally merged their types into the impl file (`claude.ts`, `github.ts`, `wakatime.ts`, `valhalla.ts`) and are imported as concrete factories. Follow the `interface.ts` style only when a second implementation or a test double is actually needed:

**Database Schema** (48 app tables in `src/db/schema.ts`, plus 4 Better Auth tables: `user`, `session`, `account`, `verification`):

*Core / GitHub*
- `users` - Extended user data with `ownTracksApiKey`, `tossNotificationApiKey`, `tossMyName`, `healthImportApiKey`, `wakatimeApiKey` (**deprecated**, see WakaTime above), `lastLat`/`lastLon`, `syncIntervalHours` (UUID PK, references Better Auth `user.id`)
- `commits`, `commitSummaries` (status: pending/processing/completed/failed), `syncJobs` (status: fetching/summarizing/completed/failed)

*Location*
- `locationPoints` - OwnTracks GPS data. Indexes on `(userId, timestamp)`, unique on `(userId, timestamp, lat, lon)`
- `placeCache` - Geocoding cache, unique on `(latKey, lonKey)`. `region`/`country` (0040) are the **structured** administrative fields the adapters now return directly (Kakao `region_1depth_name`, Google `administrative_area_level_1`, Mapbox `context.region`) instead of re-splitting the address string; they are copied into `visits.city`/`visits.countryName`. A null region can be a legitimate geocode result, not a stale row — don't treat null as "needs re-geocoding"
- `savedPlaces`, `dailyDistances`
- `visits` - Persisted stay points with reverse-geocoded placeName/address/city/countryName, optional `savedPlaceId`
- `tracks` - Movement journeys between visits; `transportationSegments` - fine-grained mode segments; `trips` - multi-day travel detection (`autoDetected` distinguishes cron-detected from user-created)
- `locationHeatmapDaily` - Per-KST-day point counts on a 3-decimal lat/lon grid, unique on `(userId, date, lat, lon)`. Precomputed so `/overview` never scans raw `location_points`
- `locationProcessingDays` - **Durable** per-day pipeline marker (`processing`/`completed`/`failed` + `attemptCount`/`lastError`/`pointCount`), unique on `(userId, date)`. Unlike the `anomaly` stamp on `location_points` it records successful *empty* days and survives a restart after a post-anomaly stage fails, and it is the watermark the overview precompute reads to decide whether an ended period may finalize
- `segmentRouteMatches` - Valhalla road-network match results, unique on `(segmentId)`. `matchStatus` is `matched`|`low_confidence`|`no_road_match`|`too_short`|`failed`|`not_applicable`. `too_short` means the segment had fewer GPS points than `MIN_POINTS_TO_MATCH` (2), so the adapter was never called — measured with the filter `loadDayPointsBySegment` actually uses (accuracy ≤200 or null, anomaly excluded), 1-point segments match 0/286 while exactly-2-point segments match 430/498 (~86%), putting the boundary precisely between 1 and 2. (A naive unfiltered count shows a higher failure rate and a blurrier boundary — always re-measure with the same filter.) `failed` is now narrowed to mean the adapter really was called and the engine/request errored. **No row = not yet processed**, so non-road modes still get a `not_applicable` row — but `stationary`/`unknown` do not. `tileVersion` distinguishes results from before and after an extract change
- `subwaySystems` (PostGIS `bbox` Polygon), `subwayLines` (MultiLineString), `subwayStations` (Point), `subwayTripMatches`

*Coding*
- `codingSessions`, `codingDailyStats` (WakaTime)
- `wakatimeConnections` - One WakaTime OAuth connection per user (0044): encrypted access/refresh tokens, `accessTokenExpiresAt`, `scope`, `status` `active`|`needs_reauth`, `wakatimeUserId` (token-response `uid`)

*Money*
- `notificationLogs` - Raw Toss/MacroDroid push payloads
- `transactions` - Parsed Toss transactions, unique on `(userId, notificationLogId)`. Also carries the AI categorization columns (`category`, `categorySource`, `categoryConfidence`, `categoryModel`, `categoryAttempts`, `categoryError`, `categorizedAt`)
- `accountRoles` - Per-user classification of Toss account names as `spending`/`default`/`ignore`
- `brokerageAccounts` - Linked KIS accounts with **encrypted** `appKeyEnc`/`appSecretEnc`, cached `accessToken`, `openedAt`, and `executionsBackfilledFrom`/`pnlBackfilledFrom` watermarks
- `holdingSnapshots` (unique `(accountId, asOfDate)`), `holdingPositions`, `brokerageExecutions` (unique `(accountId, odno, ordDt)`), `brokerageDailyPnl`, `brokerageTargetAllocations`

*Body & Health*
- `withingsConnections` - One row per user; encrypted tokens, `lastMeasureUpdate` incremental watermark
- `bodyMeasurements` - One row per Withings measurement group; typed columns for charted metrics plus lossless `rawMeasures` JSON. Unique on `(userId, withingsGroupId)`
- `healthConnections` - One Google Health connection per user; encrypted tokens, `backfillFloor`/`backfillCompletedAt`, and `healthUserId` (0045) — Google Health's own user id from `GET /v4/users/me/identity`, a **different** value from `googleSub`, partial-unique `WHERE health_user_id IS NOT NULL`. It is what webhook notifications carry. Stored at OAuth callback and lazily backfilled by `ensureHealthUserId()` (called from `syncUser` and every-tick `backfillPendingConnections`, failures retried at most hourly). `legacyUserId` is deliberately never stored
- `healthSyncState` - Per-metric watermarks: `syncedThrough` (forward cursor) and `backfilledFrom` (walks history backward). Unique on `(userId, metric)`
- `healthSamples` - Long/narrow intraday series. `value` for scalars, `valueJson` for structured metrics (sleep stages, HRV, SpO2-with-confidence). **`source` is part of the unique key** `(userId, metric, sampleAt, source)` — the same metric is legitimately written by multiple apps, and dropping `source` silently discards one source under `ON CONFLICT DO NOTHING`. `source` is resolved by `sampleSource()` as the Health Connect app package, else the measuring **platform** (Fitbit-native points carry only `dataSource.platform` = `"FITBIT"`, no `application.packageName` — reading the package alone dumped 174k rows into one `"unknown"` bucket, fixed in 0035), else `"unknown"`. Beware that some sources are **re-publishing aggregators, not sensors**: `com.withings.wiscale2` rewrites sessions it read from Health Connect, so read paths must dedup by session identity and prefer the measuring platform (`src/modules/health/sessions.ts`)
- For `heart_rate`, a row is either a raw sample or a **compacted minute bucket** whose `valueJson` carries `{ min, max, n }` — `valueJson IS NULL` is the discriminator (`src/modules/health/compaction.ts`). Anything that aggregates `healthSamples` directly must go through `bucketStats()` or read those bounds in SQL, or a bucket counts as one sample and contributes only its mean, understating daily ranges
- `healthDailySummaries` - Per-**KST**-day rollup derived by bucketing `healthSamples` via `localDaySql` (NOT copied from Google's `dailyRollUp` — a deliberate choice to keep every source and pick one per day, see below). The earlier claim that `dailyRollUp` buckets are Google-server-TZ turned out false for this account: the 2026-11-09 spike found its civil day equals the KST day (`ours / google-wearables` = 1.000 on steps). The `all-sources` rollup default, however, **sums overlapping sources** and must never be used. Rollup-only metrics (`total_calories`, `floors`) are the exception that stores the rollup itself, one row per day under source `rollup:google-wearables`. Unique on `(userId, metric, day)`
- `healthRawPages` - Verbatim API responses, append-only, never pruned, surfaced per-user in the data-usage card. Cheaper than it looks: highly repetitive JSON compresses hard, so 786k heart-rate points occupied 11 MB here against 287 MB as rows in `healthSamples`. That gap is why minute-bucket compaction is safe — this table stays the verbatim system of record

*Overview (period snapshots)*
- `periodSnapshots` - One row per `(userId, periodType, periodKey)`, unique on that triple. `periodType` is `recent`|`week`|`month`|`year`; `status` is `pending`|`computing`|`ready`|`failed`. Five independent jsonb domain envelopes (`coding`, `location`, `health`, `spending`, `assets`), each carrying its own status so one failing domain doesn't sink the snapshot. Lease columns (`computeStartedAt`/`leaseExpiresAt`/`attemptCount`/`lastError`) drive the claim queue; `computeVersion` invalidates snapshots when aggregation logic changes — bump `OVERVIEW_COMPUTE_VERSION` and every snapshot recomputes
- `periodNarratives` - AI narrative per `(userId, periodType, periodKey)`, unique on that triple, `periodType` excluding `recent`. Same lease shape (`status` `pending`|`generating`|`ready`|`failed`), plus the `model` that produced it

*Proton Drive Photos* (0048; collection layer only, nothing renders photos yet)
- `protonConnections` - One per user (`ON DELETE cascade`): `uidEnc`/`accessTokenEnc`/`refreshTokenEnc`/`keyPasswordEnc` AES-256-GCM via `src/lib/crypto.ts` (the stored session can decrypt the Proton account's Mail too, an accepted trade-off for a dedicated account), `status` `pending`|`active`|`needs_reauth`, `pending_fork_*` (selector, encrypted key, 10-min expiry; filled only while logging in, and a reconnect of an `active`/`needs_reauth` row writes only these so the live tokens survive), `volumeId` (the photos scope id), `eventCursor`, `timelineListedAt` (null means the full timeline must be listed), `backfillCompletedAt`, `lastSyncedAt`, `lastError` (fixed Korean text, never a Proton payload)
- `photos` - Unique `(userId, nodeUid)`, index `(userId, capturedAt)`. `capturedAt` is the exact UTC capture time (stored as UTC wall time like every Drizzle timestamp; verified against OwnTracks, so never re-interpret it as KST). `lat`/`lon` with `locationSource` `exif_original`|`exif`|`owntracks`|null and `locationGapSec`: precedence is the original file's EXIF GPS (`exif_original`) > Proton's extended-attribute GPS (`exif`) > an OwnTracks estimate, and an OwnTracks-derived position is **never** presented as GPS. `tags` is the raw int[] (the phone app and SDK enums disagree, so it is not interpreted), `claimedMetadata` the verified Location/Camera/Media jsonb, `originalCheckedAt`/`originalAttempts`/`originalError` (the original-EXIF marker: read once, reset by any re-ingest, 3 attempts; a format/size failure jumps straight to the cap), `imageDirection` (GPSImgDirection degrees, [0,360)) + `imageDirectionRef` (`T`|`M`; only iPhone originals carry it), `captureUtcOffsetMin` (OffsetTimeOriginal, else OffsetTimeDigitized, as minutes east of UTC), `mainPhotoNodeUid` (Live Photo parent), soft-delete `trashedAt`/`deletedAt`, `detailsSyncedAt`, `detailsAttempts` (3 strikes drop a row from selection), `thumbnailAttempts`, `locationCheckedAt`. **Exposure rule: only rows with `detailsSyncedAt IS NOT NULL` may reach any API**; rows that exist only from the timeline listing have not been through NSFW screening
- `photoBlocks` - Unique `(userId, nodeUid)`: `nodeUid`, `blockedAt`, `modelVersion` and nothing else. It is a "never fetch this node again" marker; no time, location, score or image survives a block, and ingest, event handling and reconciliation all skip these uids
- `photoThumbnails` - `photoId` FK cascade, `bytes` bytea (~50KB each, prefetched by cron because the web container never calls Proton), `fetchedAt`. Counted in the data-usage "photos" rows

*Meta*
- `dataRecoveryJobs` - Durable date-range recovery queue (0042): `fromDate`/`toDate`/`nextDate` are KST date-key **text**, `nextDate` is the per-day cursor; `status` `pending`|`running`|`completed`|`failed`, `attempts`, `leaseToken`/`leaseExpiresAt`. See **Collection Status & Recovery** below
- `healthWebhookEvents` - Google Health webhook queue (0046, `ON DELETE cascade` from `users`): one row per (user, Google dataType, operation, interval `rangeStart`/`rangeEnd`, `recordId` — `''` when absent so it fits a plain unique index). `status` `pending`|`processing`|`done`|`failed`, `attempts` (max 3), `leaseToken`/`leaseExpiresAt`/`claimedAt`. The enqueue's `ON CONFLICT` **re-arms** a done/failed row to pending (a daily interval is re-notified as the day grows), and a re-delivery landing mid-processing bumps `receivedAt` past `claimedAt` so completion re-queues instead. Done rows are pruned after 7 days, failed after 30. Counted in the data-usage "health" category
- `sourceSyncStates` - One row per `(userId, source)` (unique): `lastAttemptAt`/`lastSuccessAt`/`error`. Written by `trackSourceSync()` around pull syncs (currently WakaTime) and `recordSourceSuccess()` after successful OwnTracks/Toss ingestion and Google Health webhook receipt. `error` is always a fixed Korean message — never a provider payload

- API catch-all route: `src/app/api/auth/[...all]/route.ts` handles login, callback, session, signout
- Database hook: `session.create.after` syncs GitHub user data to app `users` table on each sign-in

Keep any new session-derived first render identical to SSR the same way
- The GitHub access token lives **only** in Better Auth's `account` table; `getGitHubToken(userId)` is the single accessor. The cron worker filters users via `EXISTS (SELECT 1 FROM account WHERE providerId = 'github' AND accessToken IS NOT NULL)` rather than reading a column on `users`

**Sync Strategy** (`src/modules/sync/service.ts`):
- Uses `getAllRepoCommits()` which iterates `/user/repos` + `/repos/:owner/:repo/branches` + `/repos/:owner/:repo/commits` (the per-repo branch walk is why a sync is more than one request per repo)
- Initial sync: last 3 months of commits. Regular sync: `lastSyncedAt − INCREMENTAL_SYNC_LOOKBACK_MS` where that constant is **72 hours** — the watermark is deliberately rewound so late-pushed commits aren't missed; only the no-watermark path is a plain 7 days. Both flows use shared `_executeSyncCommits()`
- Deduplication via SHA batch lookup (batch size: 500). Saves run in concurrent batches of `STATS_FETCH_CONCURRENCY = 3` with a 100ms pause **between batches**, not between individual saves

**Cron Jobs** (`src/lib/cron.ts` registers every schedule; some bodies live with their feature — `src/lib/trip-detection-cron.ts`, `src/modules/location/cron-processing.ts`, `src/modules/overview/cron.ts`) — all registered with an explicit `timezone: "Asia/Seoul"`. Most jobs have a module-level single-flight boolean guard, but **not all** — `reparseTodayNotifications` has none, and the two overview jobs deliberately use DB leases instead (`period_snapshots`/`period_narratives` lease columns), which is what makes them safe across processes rather than merely within one. **Cron Initialization**: `instrumentation.ts` (project root, not `src/`) uses the Next.js instrumentation hook to call `initializeCron()` on server boot. Only runs under `NEXT_RUNTIME === 'nodejs'`, and is **skipped entirely when `DISABLE_CRON=true`**. In production the web and cron workloads are separate containers built from the same image: the web container sets `DISABLE_CRON=true`, and a dedicated cron container (no published port) leaves it unset. This split exists because cron jobs (AI summaries, location/subway processing) do multi-second synchronous CPU work that blocks the Node event loop — running them in the web process stalled all HTTP requests. **Don't move background jobs back into the web container.** Note: the ingestion rate limiter (`src/lib/api-auth.ts`) and the cron single-flight guards are in-memory, single-process state — scaling either container beyond one replica multiplies the effective rate-limit quota and breaks the guards; use a shared store (or pg advisory locks, as KIS sync already does) before adding replicas. `instrumentation.ts` also initializes Sentry — unconditionally — but registers the SIGINT/SIGTERM shutdown handlers and writes the `/tmp/cistory-cron-ready` readiness marker **only in the cron branch**, so the web container has no shutdown handler and never flushes the logger on SIGTERM.

**Location Tracking & Processing** (`src/modules/location/services/`):
- OwnTracks app sends GPS data to `/api/owntracks?apikey={key}` (returns `[]` per OwnTracks protocol)
- On-demand stay-point detection for client views runs **only for today** (`/api/timeline/locations/stay-points` reads persisted `visits` for any past date). It calls `detectAndPersistVisits`, whose thresholds are `MIN_VISIT_DURATION_SEC = 180` and a *dynamic* radius — `50m × (1 + log(1 + hours))`, floored at `MIN_RADIUS_M = 15` and capped at 500m — with `MAX_VISIT_GAP_SEC = 1800` (`visit-detector.ts:15-22`). The fixed 60m/450s pair belongs to the separate `stay-detector.ts`; don't confuse the two
- Persisted `visits`/`tracks`/`transportationSegments` are computed by the daily 01:00 cron (`src/modules/location/cron-processing.ts`) and exposed via `/api/timeline/locations/*` and insights endpoints
- Pipeline stages: `anomaly-filter` → `visit-detector`/`visit-persister` → `track-builder`/`track-persister` → `transportation/detector` → `subway-match` (matches segments against `subway_lines` PostGIS geometry, groups transfers into sessions) → `subway-discovery` (probes Overpass for new cities, capped at 3/run). `trip-detector` + `/api/trips/detect` group visits into multi-day trips (overseas detection included). `backfill-orchestrator.ts` drives the re-run path
- `subway_trip_matches.leg_order` is written once by `matcher.ts` and is **segment-local** (0..n-1 within one `transportationSegmentId`) — `idx_stm_segment_leg` is a unique index on exactly that pair. `session-grouper.ts`'s post-matcher pass (Case B transfer sessions) only ever writes `session_id`; it used to also renumber `leg_order` to a session-local position, which permanently collided with that index whenever one segment's two legs landed in two different sessions (both could resolve to the same new position) and rolled back the whole day's session assignment (47 matches left `session_id IS NULL` across 12 days before this was caught). Session-local order — "is this leg first in its session", "what's the next leg in this session" — is instead derived at *read* time in `usage.ts`'s `numberedMatchesCte()`: `ROW_NUMBER() OVER (PARTITION BY COALESCE(session_id, id) ORDER BY sub_start_time, sub_end_time, id)`. One user-visible consequence: for the 47 rows that were stuck `session_id IS NULL`, the old `leg_order > 0` transfer-count filter counted their matcher-assigned second legs as transfers; the new `leg_rn > 1` counts none, since `COALESCE(session_id, id)` puts each unsessioned row in its own singleton partition — we don't actually know those were transfers, so this is the more correct number, but it is a lower one than reports showed before. `totalLegs` can also legitimately exceed the sum of legs across `totalSessions` in the same reports, because `count(DISTINCT session_id)` ignores `NULL` while that `COALESCE` partition gives every unsessioned row its own "session" for ordering purposes — pre-existing, deliberate, not a bug.
- **Transport modes use health data as ground truth** (`transportation/health-evidence.ts`, loaded once per day by `health-evidence-loader.ts` in `detectAndPersistTracks`, so the daily cron and `/api/settings/transportation-reclassify` both apply it). A deduplicated exercise session (BIKING/ELECTRIC_BIKE → cycling, WALKING/HIKING → walking, RUNNING → running) covering ≥50% of a segment wins with `high` confidence, but only below that mode's speed cap (cycling 35, walking 12, running 20 km/h) so a car leg inside a long "walk" is never relabelled; otherwise, in the 7–20 km/h band, one step source's cadence (FITBIT preferred, never summed across sources) splits cycling (<40 steps/min) from on-foot. Without evidence the classifier now calls 9–20 km/h `cycling` (walking ceiling 7 → 9): the old `avgAcceleration > 0.25 ⇒ running` split measured GPS jitter and labelled ~76% of recorded bike rides running. All thresholds come from `scripts/calibrate-mode-vs-health.ts` (read-only, train/held-out split by day) — re-run it rather than hand-tuning. The reclassify route also marks the covered `period_snapshots` pending (not narratives)
- **"Has this day been processed?" lives in `locationProcessingDays`, not in `locationPoints.anomaly`.** A day is settled when it has a `completed` row whose `pointCount` still equals the day's current point count; a mismatch (or a missing row) makes it a candidate again, which is what catches points OwnTracks flushes late for an old day. `anomaly` is now purely a quality flag — `true` for anomalous points, NULL otherwise — and every reader tests `anomaly IS NOT TRUE`. Stamping clean points `false` used to rewrite ~98% of each day's rows per run, and since `anomaly` sits in the predicate of `idx_location_points_not_anomaly` none of it could be heap-only. A **count**, not a timestamp, is compared on purpose: `locationPoints.createdAt` is UTC wall time while `locationProcessingDays.completedAt` is KST wall time
- Each day's run is bracketed by a `location_processing_days` row and reports a `failedStage` of `state`|`anomaly`|`visits`|`tracks`|`heatmap`. That row — not the `anomaly` stamp — is the durable "this day is done" signal, and `/overview` refuses to finalize an ended period until it covers the period's end date. A day marked `failed` therefore blocks period finalization rather than silently publishing a partial snapshot
- Trip writes go through `trip-writer.ts`'s advisory-lock wrapper, since detection runs from the weekly cron, `/api/trips/detect`, `/api/settings/trip-regenerate` and the backfill orchestrator
- Geocoding auto-selects Kakao (Korean coordinates), Google Places, or Mapbox (international); results cached in `placeCache`. A visit that matches a `savedPlaces` entry still goes through the coordinate lookup (for `region`/`country`) and layers the saved place's name on top — it used to skip the lookup entirely, leaving those coordinates with **no** `place_cache` row at all, which is why `scripts/backfill-visit-regions.ts` has to scan `visits` for orphan coordinates rather than just walking `place_cache`
- Trip names come from `location/services/trip-naming.ts`, which trusts only coordinate classification and Korean administrative regions. It normalizes Kakao's inconsistent `region_1depth_name` ("서울" vs "제주특별자치도") by **stripping suffixes in longest-first order**, not via an alias table, and rejects any value containing digits or lacking Hangul — a romanised value means a fallback provider answered, so the generic name is used rather than surfacing it
- Location hooks poll every 60 seconds when viewing today's date
- **File import** is a separate pipeline under `location/services/import/` backing `/api/timeline/locations/import`: `format-detector.ts` sniffs the upload, then one of `gpx-parser.ts`/`geojson-parser.ts`/`google-takeout-parser.ts` streams it, with `importer.ts` orchestrating and `job-store.ts` holding progress. Capped by `IMPORT_MAX_FILE_SIZE_MB`. Unrelated to the OwnTracks ingestion path
- Other services not part of the daily chain: `first-visits.ts`, `stay-detector.ts` (the on-demand 60m/450s clusterer), `trip-home.ts`
- **Road-network route matching** (`src/modules/location/services/route-match/`) runs after the daily pipeline (chained from `processYesterdayLocations`) and calls a self-hosted Valhalla container (`VALHALLA_URL`) to snap road-mode segments to `segment_route_matches` — see the schema entry above for its status values. **Rollout order does not matter.** `createValhallaAdapter` (`src/lib/adapters/map-matching/valhalla.ts`) distinguishes a connection-level failure — refused, DNS, reset; NOT the adapter's own timeout/abort, which stays ambiguous and is treated as an ordinary match failure — from the engine actually responding, and throws `ValhallaUnreachableError` instead of returning a `MatchResult`. `matchRoutesForDay` (`matcher.ts`) lets that propagate out of its row-building loop and returns before its single end-of-day transaction runs, so an unreachable engine makes that day write **nothing** — not even for segments matched earlier in the same call — rather than recording `failed` everywhere. "No row" is this pipeline's own "not yet processed" signal, so the day stays a candidate. **Self-healing only covers short outages, though**: the hourly catch-up unconditionally re-includes just "yesterday"/"today", and route-match failures write nothing to `location_processing_days` (that table is the core anomaly/visit/track/heatmap pipeline's marker alone), so a date that ages past that ~2-day window never re-enters `candidateDates()` on its own. An engine outage lasting longer than that — exactly the multi-day crash-loop shape the tile-build backoff exists for — leaves those dates unmatched until someone re-runs `scripts/backfill-route-matches.ts` over them. No data is lost either way, since "no row" stays truthful indefinitely. The nightly cron hook logs and moves on; `scripts/backfill-route-matches.ts`, where a human is watching and expects work to happen, fails loudly and stops instead. The `valhalla` service's `docker-compose.yml` healthcheck (`curl .../status`) is what makes "up but still building tiles" externally visible as `unhealthy` vs. `healthy`. Jenkins deploys with `docker run` and only ever runs `docker compose up -d postgres` — it never starts the `valhalla` service — so after this merges, route matching does nothing (one log line, `[RouteMatch] VALHALLA_URL is unset`) until an operator adds the three Valhalla env vars to the host `.env` and starts the container by hand; that step can now happen in any order relative to the tile build. **The base image is pinned** (`docker/valhalla/Dockerfile`: `ghcr.io/valhalla/valhalla:3.9.1@sha256:…`, never `:latest`) because tiles are a version-specific binary format — 3.8.0 removed `GraphTileHeader.date_created_` and redefined `checksum_` — and the tiles live on the `cistory_valhalla_tiles` volume, which outlives any image. `entrypoint.sh` records `valhalla_build_tiles --version` as `valhalla_version=` in `.tile_build_stamp` and rebuilds when it no longer matches the running binary, exactly like an `EXTRACTS_FINGERPRINT` change (it refuses to start if `--version` prints nothing). The version is also part of the build-failure backoff key alongside fingerprint + URL hash, so bumping the pin to pick up a Valhalla fix retries immediately instead of inheriting the old binary's backoff. **Operator implication**: stamps written before this change have no version line, so the first start after it lands rebuilds tiles once (re-download + ~5 min build; the service is down until it finishes, which the adapter treats as unreachable — nothing is written and the day stays a candidate). The same one-time rebuild happens on every future pin bump. Because `docker-compose.yml` bind-mounts `entrypoint.sh` but builds the image locally as `cistory-valhalla:latest`, the pin only takes effect after `docker compose build valhalla`; until then the new script stamps whatever version the old image reports, and the later rebuild correctly triggers another tile build
- **Regenerating transportation segments destroys route matches.** `segment_route_matches.segment_id` is `ON DELETE cascade`, and `detectAndPersistTracks` deletes and reinserts a day's `transportation_segments` with fresh UUIDs — so `/api/settings/location-backfill` and `/api/settings/transportation-reclassify` silently wipe every route match in the affected date range. Recovery is re-running `scripts/backfill-route-matches.ts` over the affected dates. This mirrors existing `subway_trip_matches` behavior, so it's consistent rather than novel — but it was written down nowhere until now

**Health & Body**:
- **Google Health (Fitbit)** — `src/modules/health/service.ts`. `HEALTH_METRICS` is a per-metric config table (`key`, dataType, camelCase `wrapper` key, `timeShape` of `interval` vs `sampleTime`, snake_case `filterField`, `valueKey`, and `agg` — `agg` is load-bearing for `recomputeDailySummaries`) ground-truthed against live payloads by the U1 spike in `docs/health/google-health-spike-findings.md`. Only metrics whose exact shape was verified are enabled; values arrive as strings *or* numbers. Sync is bidirectional: a forward incremental cursor (`syncedThrough`) plus a backward historical walk in bounded 14-day chunks (4 chunks/run) so one cron tick never pages unbounded history in a single event-loop stretch. The backward walk stops on a presence probe rather than the first empty chunk, because real data has 80+ day gaps for sparse metrics like SpO2/VO2max.
- **2026 data types** (design: `docs/superpowers/specs/2026-11-09-google-health-new-features-design.md`) — `daily_vo2_max`, `run_vo2_max`, `core_body_temperature`, `blood_glucose` are ordinary `list` rows (all empty for the owner's Fitbit Air today; the presence probe finishes their backfill in one call). `total_calories` and `floors` are **rollup-only** (`list` → 400 `UNSUPPORTED_DATA_TYPE_ACTION`): `MetricConfig.fetch: "dailyRollUp"` + `rollupFamily: "google-wearables"` (pinned by a config test — omitting it double-counts). Rollup points are anchored at 12:00 KST, `revisable`, and their backfill has no presence probe: it walks 14-day chunks down to the oldest observed **list** sample − 1 day and only completes once no list metric is still extending that bound (total-calories has empty months, so "stop at the first empty chunk" would be wrong). The `floors` value key (`countSum`) is unverified — every floors rollup has been empty. weight/body-fat/height stay unsynced: Withings owns body composition. `/health` shows `total_calories` and merges `daily_vo2_max` into the VO₂max card via `HealthMetricMeta.sourceKeys` (per day, first key wins, never blended). `scripts/calibrate-health-dominant-source.ts` is a read-only check of the dominant-source rule against Google's `google-wearables` steps rollup.
- **Sessions (`sleep` / `exercise`)** — `SESSION_CONFIGS`, time-windowed exactly like the scalars: `SYNCED_METRICS` (= `HEALTH_METRICS` + `SESSION_CONFIGS`) drives both the forward `syncedThrough` cursor and the 14-day backward backfill, so sessions do have `healthSyncState` rows. They stay out of `HEALTH_METRICS` itself (no daily summary, not in `/data-status` recovery). Only `*.interval.start_time` is rejected 400; the accepted fields (2026-11-09 probe) are `sleep.interval.end_time` (physical RFC 3339) and `exercise.interval.civil_start_time` (a **civil**, device-local day string — `timeShape: "civilInterval"`, which `buildTimeFilter` pads by one KST day on each side because the device isn't always on KST). Both are `revisable` (DO UPDATE — sessions are reprocessed after upload) and set `forwardOverlapMs` (7 days) so the forward window re-reads behind the cursor and a late phone upload isn't skipped. The previous unfiltered newest-first read under a 10-page cap only ever saw the newest ~250 of 938 workouts (38 pages, back to 2025-07-08); don't reintroduce a page-capped unfiltered read. They also skip `healthDailySummaries` (a night is a hypnogram, not a daily average), so they are read straight from `healthSamples` — which means the multi-source dedup that `recomputeDailySummaries` gives scalars for free has to be applied at **read** time via `src/modules/health/sessions.ts`. It keys on the start **second**, not the exact instant: an aggregator republished the same workout 389 ms apart, which an exact-timestamp key read as two sessions and double-counted.
- **Compaction** — `src/modules/health/compaction.ts` buckets settled `heart_rate` rows by minute (see the `healthSamples` note above). Compacts *closed* ranges out of stored rows rather than bucketing at ingest: a sync window can end mid-minute, so ingest-time bucketing builds one bucket twice from partial data, and an associative merge there breaks idempotency because a re-fetched window double-counts `n`. Here the contributing raw rows are deleted in the same transaction, so the merge can't double-count. `RAW_RETENTION_DAYS = 3` and `MAX_DAYS_PER_RUN = 7`.
- **On-device import** — `/api/health-import?apikey={key}` (`src/modules/health/import.ts`) ingests raw Health Connect records pushed by a phone automation, backfilling sleep/exercise that Google's cloud sync does not carry — Google's cloud never held the Samsung-era sleep sessions at all, so this endpoint is the only route to that history. Idempotent via `onConflictDoNothing` on the `(userId, metric, sampleAt, source)` key. Its payload is raw Health Connect shape (epoch-millis times, numeric stage codes), distinct from the cloud shape; `src/modules/health/sleep.ts` normalizes both. `pickSource` falls back to `'healthconnect'`, never `'unknown'` — which is what makes `source = 'unknown'` a safe proxy for "cloud-path, unattributed". `GET /api/health-import` is a session-authed verification view.
- **Withings** — `src/modules/withings/service.ts` syncs measurement groups incrementally off `lastMeasureUpdate`; display formatting is centralized in `src/lib/body-format.ts` so insights and reports never diverge.
- **Privacy**: `src/lib/telemetry-privacy.ts` (`redactSearchEvent`/`redactSearchStreamedSpan`/`redactSearchBreadcrumb`) is wired into **all three** Sentry inits and strips query strings from any `/search` or `/api/search` URL in requests, referrers, breadcrumbs, spans and the error trace context — search terms are personal data. `src/lib/sentry-scrub.ts` is wired into `sentry.server.config.ts`'s `beforeSend` (`scrubHealthData`) and `beforeSendSpan` (`scrubHealthSpan`) and drops raw health payloads (URL markers, breadcrumb data, query/body/auth span attributes, denylisted `extra`/attribute keys). Any new field carrying health values must be added to its denylist. It also covers Proton: the URL markers `proton.me`, `/api/proton` and `/api/photos`, and the denylisted keys `latitude`, `longitude`, `claimed_metadata`, `thumbnail`, `key_password`, `exif`, `image_direction`, `utc_offset` (plus camelCase variants), so photo coordinates, EXIF-claimed metadata, camera headings, capture offsets, thumbnail bytes and key material never reach Sentry. **Sentry v11 specifics**: spans are *streamed* (`traceLifecycle: "stream"`, pinned explicitly in every init so `SENTRY_TRACE_LIFECYCLE=static` can't silently bypass the hooks), so `beforeSendTransaction` never fires and `beforeSendSpan` receives `StreamedSpanJSON` (`name`/`attributes`, not `description`/`data`) for every span including the segment span. And v11 replaced `sendDefaultPii` with `dataCollection`, which **collects everything when unset** — every init must pass `SENTRY_DATA_COLLECTION` (v10's no-PII posture). `src/lib/sentry-hooks.test.ts` runs the real SDK with a capturing transport to prove both.

**Overview** (`src/modules/overview/`) — the unified reporting surface, and the piece most likely to surprise you:
- `/overview?periodType=&periodKey=` renders one of four period types (`recent`|`week`|`month`|`year`). `/insights`, `/report` and `/report/comparison` are **redirect-only shims**: `legacy-routes.ts` maps their old query params onto overview params. Don't add UI to those pages — they render nothing
- Their **API** routes are not deprecated, though. `modules/insights` still backs `/api/insights` (the `/health` page reads its `body` section); `modules/report` still backs `/api/reports/*` and `location/services/trip-naming`. Neither module is dead code — only the two pages are
- Reads never aggregate on demand. `GET /api/overview/history?periodType=week|month|year&periodKey=` (`history.ts` + `history-store.ts`) feeds the hero's change-vs-previous and its 10-period bars from *stored* snapshots only: a period without its own snapshot is filled from the daily series of a stored larger snapshot covering it (a year carries every day), and one nothing covers stays `null`, never 0. The store selects only the jsonb paths it needs, never the heatmap payloads. `GET /api/overview` returns a stored `period_snapshots` row, or a `missing`/`pending`/`computing` status that the client polls on. `POST /api/overview/recompute` enqueues (202) and is same-origin-checked, capped at `OVERVIEW_OUTSTANDING_LIMIT` (5) outstanding requests per user
- `precompute.ts` is a leased work queue, not a loop: `recoverExpiredLeases` → `seedActivePeriods` → `claimSnapshots` (10-min lease, batches of 5 claimed repeatedly until a 3-minute run budget is spent, each row at most once per run, 3 attempts, 250 users per page) → `publishSnapshot`. Every publish is conditional on still holding the lease, so a second worker can't clobber a first. Claim order (`getClaimPriority` mirrors the SQL; pinned by `precompute.integration.test.ts`): current periods that need work first, then pending/failed week/month/year backlog, finalization, old versions, routine refresh of ready current periods, and old `recent` keys last — round-robin across users within a tier, newest period end first. Never order by `updatedAt` alone: an invalidation that re-marks history and then the current periods would park the current ones behind the whole backlog
- A `pending`/`computing` row keeps its last envelopes (invalidation and recompute never clear them), so `GET /api/overview` serves it as `{ stale: true, computedAt, domains }` and the page renders it with a small 업데이트 note; the full computing state is only for a row that has never been computed. The client polls with a 3 s → 10 s → 30 s back-off, paused while the tab is hidden
- **Active periods refresh freely; ended periods only finalize once `location_processing_days` covers their end date** (`deferredForLocation` in the run result). An ended month finalized before its last day's location pipeline landed would freeze a permanently wrong number
- `aggregate/` computes the five domains (`coding`, `location`, `health`, `spending`, `portfolio`) into independent envelopes; a domain that throws is stored `failed` while the others publish
- `narrative.ts` generates the AI narrative for non-`recent` periods on the same lease pattern (batch 5, 3 attempts, 8-min lease). Input is bounded by `NARRATIVE_MAX_INPUT_TOKENS` (60k), measured with a real `countTokens` call; `NARRATIVE_MAX_INPUT_CHARS` (120k) is only the local char proxy used to pick a candidate before spending that call, and the sole bound when counting is unavailable or fails. Truncation drops per-domain detail to a preview length **binary-searched against the remaining budget**, so overshooting the limit costs proportionally rather than collapsing to a fixed floor — the earlier fixed-preview version cut the year snapshot from 118,240 to 12,165 chars. The count covers the data envelope only (not `system`), so it under-measures the real request slightly. The producing model is recorded on the row
- `OVERVIEW_RETENTION_PERIODS` (45 recent, 104 week, 60 month, 10 year) bounds how far back a period may be requested or recomputed — a key older than the boundary, or newer than the current one, is rejected rather than queued

**Travel** (`src/modules/travel/`):
- `/travel` lists trips (cursor-paginated on `(endDate, startDate, id)`) and `/travel/[tripId]` shows one, joining visits, commits, coding, spending and health for the trip window. `GET /api/trips?limit=&summary=1` adds a `summary` (`TravelService.getListSummary`) for the hero: every trip overlapping the current KST year plus `spendingSince`, the first Toss transaction date (the date spending coverage starts, for the hero)
- `POST /api/trips/[id]/not-a-trip` is the correction path for a false positive: rather than just deleting the trip, `not-a-trip.ts` creates a `savedPlaces` exclusion around the trip's dominant visit (10 km radius, or 100 m when pinned to an existing saved place) so auto-detection stops re-detecting it on the next weekly run

**Search** (`src/modules/search/`, `/search`, `GET /api/search`):
- `searchRecords()` builds one `UNION ALL` over commits, transactions, visits (with the owner's current saved-place name) and trips, every branch filtered by `user_id`, ordered `occurred_at DESC, source, id` and paginated in Postgres (30/page, max 100 pages). `q` is a **literal** `ILIKE` — `\`, `%`, `_` are escaped
- Range bounds are bound as `toISOString()` and cast `::timestamp` explicitly so the connection's session timezone can't reinterpret them (the integration test runs under a non-UTC session). Visits match by interval **overlap** and link to their actual start day; trips compare KST date strings directly
- `parseSearchInput()` (`input.ts`) defaults to the last 30 KST days, caps the range at 366 days and `q` at 200 chars, and throws `ApiError(400)` with Korean messages. The route rethrows DB errors as a generic error because Drizzle errors can embed the query parameters, i.e. the search term, and responds `Cache-Control: private, no-store`
- Result links: commits → the GitHub commit, trips → `/travel/[id]`, everything else → `/dashboard?date=` (KST day)
- Redesign additions: `?category=<expense category>` limits to spending rows of that category (400 on an unknown key); `?hours=H-H` is a KST hour-of-day window (start inclusive, end exclusive, wraps past midnight when start > end, e.g. `22-3`) that excludes trips. The response carries `counts` — per-source totals for the same filters ignoring `source` — and items now include `occurredAt`, `amount`, `category` and `repository`. `nl-parser.ts` (`parseNaturalQuery`) is a **rule-based, model-free** client-side reader of free text ("지난주 저녁 배달") into dates/sources/category/hours chips plus the literal remainder

**ECG / irregular-rhythm notifications (optional scopes)** (`src/modules/health/rhythm.ts`, design §5):
- **Scopes:** `googlehealth.ecg.readonly` / `googlehealth.irn.readonly` are `GOOGLE_HEALTH_OPTIONAL_SCOPES` and are **not** in the default connect set. The settings Google Health card's "ECG/불규칙 심박 연결" button runs `/api/fitbit/authorize?extra=ecg,irn` (default scopes + extras, `include_granted_scopes`), and the callback stores the granted `scope`.
- **Granted means stored:** Google's granular consent lets the user untick either scope, so everything keys off `hasHealthScope(connection.scope, …)`. `syncUser` only adds ECG/IRN units for granted scopes, which keeps 403s out of `lastSyncError`.
- **Sync:** not in `SYNCED_METRICS` (no chunked backfill, no daily summary, no `/data-status` recovery). ECG's filter supports only `>=`, so the first run reads `>= backfillFloor` and later runs read `>= syncedThrough − 1d`, paging to the end (`MAX_PAGES_PER_WINDOW` backstop). IRN's filter field is undocumented; a 400 falls back to an unfiltered read.
- **Storage:** summaries only, in `health_samples`: `ecg` (value = avg bpm, `valueJson` = classification/sampling/lead/device, **no waveform**) and `irn` (value = positive alert windows, `valueJson` = windows **without heartBeats**). `health_raw_pages` keeps the verbatim responses as for every type. Upserts are DO UPDATE.
- **Display:** the /health "심전도 · 불규칙 심박" card is shown only when `/api/fitbit/summary` returns `rhythm`. It relays the device classification in Korean with a "의료 진단이 아닙니다" note and never re-interprets a trace.
- **Privacy:** never part of `/overview` — `OVERVIEW_HEALTH_METRICS` is an explicit allowlist, and a test pins that ecg/irn can't reach the snapshot or the Anthropic narrative. Sentry scrub denylists their payload keys.
- **Unverified shapes:** the owner's Fitbit Air has no ECG, and neither scope had been granted when this was written, so the parsers follow the documented shapes defensively. Confirm the live payloads after re-consent.

**Google Health webhooks** (design: `docs/superpowers/specs/2026-11-09-google-health-new-features-design.md` §4):
- **Purpose:** cut the forward-sync delay from ~24h (the 24h-gated `syncUser`) to minutes. Polling and backfill stay unchanged as the safety net, because webhooks cover no history, several types (spo2, vo2-max, active-energy, daily-vo2-max, core-body-temperature) and possibly no Health-Connect-sourced data.
- **Receive (web container)** — `POST /api/fitbit/webhook`, no session:
  - body cap 256 KB (413), then the raw bytes are read
  - `Authorization` must equal `GOOGLE_HEALTH_WEBHOOK_SECRET`, compared with `timingSafeEqual` over SHA-256 digests. A mismatch is 401, rate-limited per IP under `gh-webhook-unauth`. That 401 is also the anonymous leg of Google's verification handshake
  - `{"type":"verification"}` → 200
  - ECDSA signature check (`src/lib/google-health-webhook-signature.ts`, described below), in `log-only` or `enforce` mode
  - `healthUserId` → user through `health_connections.health_user_id` (one batched lookup, active connections only)
  - enqueue into `health_webhook_events` → **204**
  - **DELETE notifications are logged and ignored** (lossless archive; reflecting deletes would need a record-id column on `health_samples`). Unknown users are dropped and counted. Logs carry counts, data types and operations only — never `healthUserId` or interval times. Google calls nothing in this path.
- **Signature** — `src/lib/google-health-webhook-signature.ts` is a minimal Tink reimplementation with Node `crypto`, since there is no Tink for Node:
  - fetches the keyset JSON from gstatic and parses the `EcdsaPublicKey` proto with a tiny protobuf reader (x/y arrive as 33-byte sign-padded integers)
  - signature = `0x01 ‖ keyId(4B BE) ‖ DER(r,s)`, verified over the **raw** body
  - the keyset is cached in memory (6h TTL); an unknown key id forces one refetch, rate-limited to 1/min
  - `GOOGLE_HEALTH_WEBHOOK_SIGNATURE_MODE=log-only` (the default) logs every outcome with running totals (`totalVerified`/`totalFailed`/`totalUnavailable`) and never rejects. `enforce` answers 401 on failure and 503 on a cold keyset outage, so Google retries
  - the parser was checked against the live keyset (5 TINK P-256/SHA-256/DER keys) and the msavas2544/google-health reference parser
- **Consume (cron container)** — `health-webhook` task, every minute, **only when `GOOGLE_HEALTH_WEBHOOKS_ENABLED=true`**. `processHealthWebhookQueue` (`src/modules/health/webhook-queue.ts`):
  - prunes old rows, then claims ≤200 events with `FOR UPDATE SKIP LOCKED` + a lease token (5-min lease, 3 attempts)
  - groups claimed events per (user, dataType), ≤20 types per user per tick
  - for every `SYNCED_METRICS` type (scalars, rollups and the time-windowed `sleep`/`exercise` sessions): merges the intervals into one window (±1h pad, ≤14 days; the rest is released for the next tick) → `refreshMetricWindow`, i.e. the normal list/rollup fetch + upsert + daily recompute. It **never moves `syncedThrough`**, because webhook windows are not contiguous
  - types we don't store complete as ignored
  - **`weight` triggers one early Withings sync** (`syncUser` with a 15-min `skipIfSyncedWithinMs`, so a burst runs once)
  - **errors:** an inactive or reauth connection fails terminally; other errors retry, storing a fixed Korean `lastError`
  - **overview invalidation:** windows touching a *past* KST day re-queue that range's `period_snapshots` through data-status's `invalidateRecoveredPeriods(…, { narratives: false })`. Today's data only touches active periods, which refresh anyway, and narratives are left alone so late data never re-spends an Opus call
  - Settings shows "실시간 동기화 마지막 수신" (`max(received_at)`)
- **Operator registration (one-off, after deploy)** — the subscriber is project-level and NOT created by the app:
  1. Generate a secret (`"Bearer $(openssl rand -hex 32)"`), put it in the host `.env` as `GOOGLE_HEALTH_WEBHOOK_SECRET`, and set `GOOGLE_HEALTH_WEBHOOKS_ENABLED=true` (both containers share `--env-file`). Deploy.
  2. Check that the reverse proxy / Cloudflare in front of `cistory.hojoon.dev` passes the `Authorization` header and raw body through untouched and doesn't bot-block UA `Google-Health-API-Webhooks`:
     - `curl -i -X POST https://cistory.hojoon.dev/api/fitbit/webhook -H "Authorization: $SECRET" -d '{"type":"verification"}'` → **200**
     - the same request without the header → **401**
  3. On the operator Mac (gcloud logged in as the project owner): `GOOGLE_HEALTH_WEBHOOK_SECRET="$SECRET" npx tsx scripts/google-health-subscriber.ts create` (use `--dry-run` first, and `--exclude total-calories` if Google rejects that type). The script uses `gcloud auth print-access-token`, project **number** `794779085130` (the project id 403s) and `x-goog-user-project`, and creates one `AUTOMATIC` subscriber `cistory-prod` for the types in `WEBHOOK_DATA_TYPES` (heart-rate and weight included). Google runs the verification handshake synchronously; `FAILED_PRECONDITION` means step 2 isn't right. Confirm with `… list` / `… get`.
  4. Observe: Better Stack `[HealthWebhook] notifications received` / `queue tick` logs, Settings' "실시간 동기화 마지막 수신", and the GCP "subscriber errors" metric.
  5. Once a few real notifications log `ok: true` on `[HealthWebhook] signature checked`, set `GOOGLE_HEALTH_WEBHOOK_SIGNATURE_MODE=enforce` and redeploy the web container.
  6. Rollback: `… delete --yes` (Google keeps retrying undelivered notifications for 7 days otherwise), or just unset `GOOGLE_HEALTH_WEBHOOKS_ENABLED` to stop consuming.

**Proton Drive Photos** (`src/modules/proton/`, design: `docs/superpowers/specs/2026-11-10-proton-drive-photos-design.md`; originals stage: `2026-11-10-proton-original-exif-design.md`):
- **Connect** (Settings card, `ProtonSettings.tsx`): `connection.ts` starts a session fork (`POST /api/proton/connect`), the user logs in on Proton's own page, and `connect/status` polls once per request (422 means not ready). `GET /api/proton`'s `forkPending` (an unexpired `pendingForkExpiresAt`) keeps the client polling after a reload, including a reconnect from `active`/`needs_reauth`, whose `status` never reads `pending`. Cistory never sees the password. Reconnecting to the same `volumeId` keeps photos and forces one `tree_refresh`-style reconciliation; a different volume wipes photos before re-backfilling. Either way a superseded session (different uid) is best-effort revoked after the commit, since it can decrypt the whole account; a fresh session that ends up stored nowhere (volume lookup failed, a concurrent disconnect, a restarted fork, an unreadable row) is revoked too. `needs_reauth` is set only on a 4xx refresh failure (not 429) whose stored token still equals the one used; network errors and 5xx never flip it. `x-pm-drive-requirements` responses are logged so an SDK-upgrade-required failure is distinguishable from a re-login one
- **Sync** (cron container only; web never calls Proton): `sync.ts` orchestrates `events.ts` (cursor-based `iterateEvents`: created/updated upsert, deleted soft-deletes, `fast_forward` moves the cursor, `tree_refresh` and a rejected cursor reset `timelineListedAt`/`backfillCompletedAt` for a full reconciliation, `tree_remove` sets `needs_reauth`; the cursor is saved in the same transaction as the batch; when the classifier is unavailable the batch's deletions are still applied in their own fenced transaction without moving the cursor), `backfill.ts` (baseline cursor first, one timeline listing per backfill, then 500 detail rows per tick via `iterateNodes`, 3 attempts per row; Live Photo children listed only through their main photo are not deleted by reconciliation), and `location.ts`. All token-bearing writes are fenced by the per-user `proton-token` lock. Cron-side Proton failures become fixed Korean `lastError` text only
- **Originals** (`originals.ts`, after events and details, before the location fill): two bounded parts per tick. *Thumbnail recovery* (`THUMBNAIL_RECOVERY_BATCH_LIMIT` 10) takes hidden rows whose `details_error` is `thumbnailMissing`/`thumbnailUnclassifiable` **regardless of `details_attempts`** (so the ~350 2020 photos Proton has no thumbnail for re-enter without an attempt reset), re-reads the node, downloads the whole original (verified `downloadToStream`, `ORIGINAL_MAX_BYTES` 32 MiB cap checked on the claimed size and while streaming; a signature-only completion failure is accepted), builds a ≤512 px metadata-free JPEG (`original-thumbnail.ts`: sharp for JPEG/PNG/WebP/AVIF with EXIF orientation applied, **`heic-decode`/`libheif-js` wasm** for HEIC since sharp's prebuilt libvips has no HEVC; animations, HEIF sequences, >50 MP or >16.8 MP HEIC fail closed) and runs the SAME `screen()` as ingest: pass stores that JPEG + the original's EXIF, block deletes and writes `photo_blocks`, an undecodable original stays hidden (`originalUndecodable`, attempts jump to the cap). It is skipped while the classifier is down. *EXIF* (`ORIGINAL_EXIF_BATCH_LIMIT` 60) takes exposed image rows (`media_type` NULL or `image/%`; videos are neither read nor counted) with `original_checked_at IS NULL`, newest first, and parses EXIF through exifr's chunked reader over the SDK seekable stream (`original-source.ts`, windowed cache so backward seeks never re-fetch a 4 MiB block; nodes without claimed block sizes fall back to the capped full download). Proton blocks are 4 MiB, so a read costs one block (JPEG, early HEIC Exif item) or two (a >4 MiB HEIC with its Exif item at the end). exifr ignores HEIF `iloc` base offsets (device HEICs use extent offsets, which it handles). Each photo's write is its own fenced transaction (`assertConnectionUnchanged`), conditional on the row still being unread. Error handling: auth/rate-limit/fence errors propagate to the tick; `ConnectionError`/5xx (`isTransientOutage`) stop the stage without charging; a decoder load failure is `ClassifierUnavailableError` (stops recovery only); oversize/undecodable is permanent; anything else (timeout after `ORIGINAL_DOWNLOAD_TIMEOUT_MS` 60 s, decryption, 404) is +1 attempt. A pass from ingest (any `node_created`/`node_updated` re-ingest) resets the marker so the new revision's original is read again
- **Location fill** (`location.ts`): rows without GPS (`location_source` NULL or `owntracks`; neither `exif` nor `exif_original` is ever touched) get the nearest `location_points` fix (`anomaly IS NOT TRUE`) within +/-15 minutes as `owntracks`. The result is finalized only once the capture's KST day has settled (`location_processing_days` completed with matching `point_count`, same rule as `candidateDates()`) or is older than the 45-day pipeline window; before that it is recomputed each tick. The SQL assumes `photos.captured_at` and `location_points.timestamp` are both UTC wall time, pinned by the integration test
- **NSFW pre-blocking** (`nsfw/`): thumbnails are classified in memory by local NSFWJS (`nsfwjs@4.4.0` MobileNetV2, `NSFW_MODEL_VERSION`) on the TensorFlow.js **wasm** backend (the image is Alpine/musl, so no native tfjs-node; weights ship in the image, nothing is downloaded at runtime; photos are never sent to any external service). Thumbnails are decoded by **`sharp`** (`nsfw/decode.ts`, explicit dependency pinned to the version Next resolves; libvips prebuilt, `@img/sharp-linuxmusl-*` on Alpine) to 3-channel sRGB. The format allowlist is JPEG, WebP (Proton's Type1 thumbnails are often extended `RIFF....WEBPVP8X`; the earlier JPEG-only `jpeg-js` decoder failed ~84% of a production backfill as `thumbnailUnclassifiable`), PNG and still AVIF, checked by magic bytes (`modules/proton/thumbnail-format.ts`) **and** sharp's metadata; anything else, animations (WebP/AVIF with >1 page, APNG), truncated input or >4 MP throws `ClassifyInputError`. Alpha is flattened onto white, so the screen sees what a viewer sees. sharp failing to load is `ClassifierUnavailableError` (infrastructure, burns no attempts). `nsfwjs`, tfjs, `sharp`, `exifr`, `heic-decode` and `libheif-js` are `serverExternalPackages`; Next's standalone tracing already copies `sharp` + the platform `@img/*` packages (the builder stage runs on Alpine, so the image gets the musl binary). Block when `porn + hentai >= 0.5` or `sexy >= 0.8` (`NSFW_BLOCK_*`, deliberately over-blocking, tunable). A block deletes the row, extends to the node's related Live Photo uids (also recorded in `photo_blocks`), drops the thumbnail bytes and writes only `photo_blocks` markers; bytes, scores and uids are never logged or sent to Sentry. **Fail-closed**: a model load, decode or missing-thumbnail failure stores no thumbnail and does not finalize details (`detailsAttempts` rises; after 3 the row stays without a thumbnail until the originals stage's thumbnail recovery screens one generated from the original), so no unscreened image has a path into the database. `scripts/rescreen-photo-thumbnails.ts <userId> [--apply]` re-screens stored thumbnails after a model or threshold change (dry run by default; a thumbnail that can no longer be decoded is hidden for re-screening, never blocked; it holds the sync's `proton-sync:<userId>` session lock and aborts if a tick holds it)
- **Privacy/teardown**: `/privacy` lists Proton photo metadata (including the original's EXIF GPS, camera heading and capture UTC offset) and thumbnails, states that sensitive images are filtered on the server and not stored, and that originals are read in memory only (EXIF, thumbnail recovery) and never stored. The Settings card and `/data-status` notes show only the count `원본 메타데이터 확인 N/M`. Account deletion best-effort revokes the Proton session in `src/app/api/auth/disconnect/route.ts` via `ProtonConnectionService.revokeOnly` before `deleteAccount()` runs (`account-deletion.ts` itself makes no Proton call; the `users` cascade handles the rows). Operational unknowns (token lifetimes, event latency, CAPTCHA on server IPs, Live Photo presentation, NSFW accuracy on Korean/Galaxy thumbnails, the late-2026 Proton crypto change) are listed in spec section 6

**Collection Status & Recovery** (`src/modules/data-status/`, `/data-status`):
- `GET /api/data-status` reports eight sources (`github`, `location`, `toss`, `wakatime`, `kis`, `withings`, `health`, `proton`): connection/reauth state, `sourceSyncStates` timestamps, last record, and a per-KST-day grid over a ≤31-day range ending today. A day with zero records is `unknown`, not "empty" — only a completed recovery can mark it `checked` (`model.ts`). A connected source with no success in 48h is `stale`
- `proton` is **not recoverable** (it reconciles itself through the event stream and `tree_refresh`); it shows the blocked count (a number only) and the count of photos that exhausted their detail attempts. Per-day counts use `localDaySql(photos.capturedAt)`
- `POST /api/data-status/recover` (202) only accepts `RECOVERABLE_SOURCES` = `wakatime`, `withings`, `health` (Google Health scalar metrics). Other sources get source-specific instructions instead — phone-only Health Connect data, sleep/exercise sessions, missed Toss notifications and historical KIS snapshots can't be re-fetched and are never fabricated
- `enqueueRecovery` serializes per user+source with `pg_advisory_xact_lock` (409 `RECOVERY_ACTIVE` if one is pending/running). The cron worker claims one day at a time with `SKIP LOCKED` and a UUID lease token (5-min lease, heartbeat-extended), advances `nextDate`, and completes with a fenced write; abandoned jobs are retried up to 3 times. Completion or failure invalidates the affected `period_snapshots`/`period_narratives` so `/overview` recomputes
- Health recovery stages a full metric-day response, then replaces that source's rows and rebuilds the daily summary in one transaction, sharing a per-user lock with heart-rate compaction. An empty provider response never deletes existing history

**Toss Transaction Tracking**:
- MacroDroid forwards Toss push notifications to `/api/toss-notifications?apikey={key}`
- MacroDroid sends multi-line notification text as literal LF/CR/TAB inside JSON strings, i.e. invalid JSON. `sanitizeMacrodroidJson()` (`src/modules/transaction/payload.ts`) escapes control chars only inside strings, and the ingestion route **and** `reparse-service.ts` both decode through `decodeNotificationPayload()` there — the reparse path couldn't decode any multi-line notification before they shared it
- Raw notification stored in `notificationLogs`, then parsed by `src/modules/transaction/parser.ts` (type `deposit`/`withdrawal`/`cancel`, amount, merchant, account name, `isSelfTransfer`). Beyond card payments/transfers it parses completed 자동이체, 요금납부 출금 and "N원 결제 취소"; self auto-transfers (적금/투자) are flagged `isSelfTransfer`. The trailing card balance ("잔액 N원") is stripped from payment merchants
- Deduplication: unique constraint on `(userId, notificationLogId)` plus a ±2 minute time-window duplicate check that **includes the notification body** — with the balance stripped from the merchant, back-to-back same-amount purchases would otherwise collapse into one
- Daily 23:00 reparse picks up notifications that failed with older parser versions
- **Spending buckets** (`src/modules/spending/classify.ts`): `classify()` (JS) and `bucketSql()` (SQL `CASE`, needs the `account_roles` LEFT JOIN in scope) must stay in lockstep — both resolve a row to `spending`|`income`|`ignore`. Order: `spendingOverride` → `cancel` rows ignored → a withdrawal voided by a later same-account/merchant/amount `cancel` within `CANCEL_WINDOW` (30 days, `cancelledSql()`) ignored → account role. A `spending`-role (pooled) account counts **only** the user's own deposits into it (`isSelfTransfer` or merchant = `tossMyName`) that are *not* mirrored by a same-amount withdrawal from another account (`mirrorWithdrawalExistsSql()`) — otherwise money moved in and then spent was counted twice. Changing these rules requires bumping `OVERVIEW_COMPUTE_VERSION` (now 4) so spending snapshots recompute
- **Refunds inside income** (`src/modules/spending/refund.ts`): Toss reports a refund as an ordinary deposit from the merchant, so it stays in the `income` bucket (buckets are unchanged). `GET /api/spending` marks such rows `isRefund` (`refundSql()`: payer's `merchantBase()` matches a merchant the user paid for a categorized purchase, excluding `gift`/`finance` payees) and adds `summary.flow` (`summarizeIncomeFlow()`: refund vs. other money received, with the top merchant/account) for the page's 순지출 view
- **One-off charges in the forecast** (`forecast.ts`): a single charge above `oneOffThreshold()` (0.2 × the median completed month, backtested) is added back once rather than extrapolated; `GET /api/spending/trend`'s `forecast` exposes `oneOffTotal`/`oneOffCount`/`oneOffThreshold`, and monthly bars gained a `key` (`YYYY-MM`, since `month` alone repeats across the 13-month window)
- Categorization is a separate async pass: `src/modules/spending/category-classifier.ts` batches 25 transactions per Haiku call into the fixed `EXPENSE_CATEGORIES` list (`categories.ts`), records confidence/model/attempts, and never blocks ingestion

**KIS Brokerage Portfolio** (`src/modules/portfolio/`):
- `service.ts` (`PortfolioSyncService`) drives KIS sync: daily `holdingSnapshots`/`holdingPositions`, `brokerageExecutions`, `brokerageDailyPnl`. Access tokens cached on `brokerageAccounts` and refreshed lazily (60s grace); app key/secret AES-256-GCM encrypted via `src/lib/crypto.ts`
- `backfillPendingAccounts()` walks each account back to `openedAt`, advancing the backfill watermarks so it's idempotent and resumable across cron runs (also exposed as `/api/portfolio/accounts/[id]/backfill`)
- `returns.ts` computes TWR over `tot_evlu_amt` **alone** — KIS `tot_evlu_amt` already includes the cash deposit, so adding `deposit` on top double-counts every external deposit as fake gain. It infers cashflows from deposit deltas reconciled against a **T+2 business-day settlement** model and anchors every account's series to the `RETURNS_EPOCH` of `2026-05-12` (earlier snapshots include pre-settlement receivables that inflate the baseline). That constant is **not** in `returns.ts` — it lives in `src/app/api/portfolio/returns/route.ts` and is duplicated in `scripts/verify-returns.ts`, so changing the epoch means editing both

**Logging**: `src/lib/logger.ts` wraps Better Stack (Logtail) with `info`, `warn`, `error`, `flush`. Falls back to console when `BETTER_STACK_SOURCE_TOKEN` is not set. `@logtail/node` 0.6 requires an `endpoint`; `logger.ts` passes `BETTER_STACK_INGESTING_HOST` or, when unset, `https://in.logs.betterstack.com` — the default copied from `@logtail/core@0.5.8`, so no new config is needed.

### Database Operations

1. Modify `src/db/schema.ts`
2. `yarn db:generate` to create migration files in `drizzle/` — review the generated SQL before committing
3. `yarn db:migrate` to apply to PostgreSQL (local dev)

`drizzle.config.ts` resolves `DATABASE_URL` as `DRIZZLE_DATABASE_URL` env var > `.env.local` > `.env` > the localhost fallback below, loading `.env.local` with dotenv's `override: true` because drizzle-kit's CLI auto-loads `.env` first (default `override: false`) — without it, `.env.local` is a silent no-op. Fallback `DATABASE_URL` for local dev: `postgresql://cistory:cistory@localhost:5432/cistory`.

CI/production uses `scripts/migrate.ts` (`npx tsx scripts/migrate.ts`) rather than `drizzle-kit migrate`. That script sets `lock_timeout=60s` and `statement_timeout=2m` at the connection level so a stuck `__drizzle_migrations` lock fails the build fast instead of hanging Jenkins. Jenkins additionally kills stale `idle in transaction` sessions on `drizzle`/DDL queries before starting a run.

**PostGIS extension upgrades are not migrations.** Before running the Drizzle migrations, `scripts/migrate.ts` calls `upgradePostgisExtensions()` (`scripts/lib/postgis-extensions.ts`), which runs `ALTER EXTENSION … UPDATE` for each installed `postgis`/`postgis_raster`/`postgis_topology`/`postgis_sfcgal` whose `installed_version` lags the image's `default_version` (postgis first), and is a no-op otherwise. It can't be a one-shot migration: pulling a newer `postgis/postgis` image onto the existing volume swaps the library but not the catalog, and Jenkins' `docker start cistory-db || docker compose up -d postgres` **never recreates an existing container**, so the image swap is a manual operator step (`docker compose up -d postgres` from the compose project that owns `cistory-db`) that may land before or after the deploy carrying the new tag — a migration that ran first against the old image would be recorded as applied and never re-run. Extensions the image no longer ships (PostGIS 3.7 dropped `postgis_tiger_geocoder`/`address_standardizer`; pre-3.7 docker-postgis images auto-installed the tiger geocoder + `fuzzystrmatch` into `POSTGRES_DB`) are only warned about, never dropped. The migrator Docker stage copies `scripts/lib/postgis-extensions.ts` explicitly — keep that `COPY` if the file moves.

### CI/CD & Deployment

- **Jenkins pipeline** (`Jenkinsfile`): GitHub webhook → **Test** (`docker build --target tester`, whose `RUN yarn test` fails the build on any Vitest failure, before the image is built) → **Browser Regression Tests** (`docker build --target browser-tester`, Debian, production-mode Playwright) → **Integration Tests** → Docker build → Drizzle migrations (separate `migrator` stage container) → deploy web + cron containers → health check against `/api/health` (15 attempts, 5s interval) → Telegram notification. Everything from Run Migrations onward is gated on `when { branch 'main' }`, so PR builds test and build but never deploy.
- **Integration Tests stage**: `src/**/*.integration.test.ts` execute real SQL and can't run inside `docker build` the way the Test stage does — a build has no network route to a sibling service container. This stage instead mirrors the "Run Migrations" stage's own shape: build the `integration-tester` target (full source + deps, nothing run at build time), bring up `docker-compose.test.yml`'s throwaway Postgres, then `docker run --network host` the image against it, migrating then running the suite inside the container. Because this is a Multibranch Pipeline — every branch and every open PR is its own Jenkins job, so concurrent builds on the shared agent are the normal case, not an edge case — CI never uses the compose file's local-dev defaults directly: it passes `-p <BUILD_TAG, sanitized>` to scope the compose project (and, since the service has no hardcoded `container_name`, the container too) per build, and `TEST_DB_HOST_PORT=0` to get an OS-assigned ephemeral port instead of the fixed `5433` local dev uses, reading the real port back via `docker compose port` to build `TEST_DATABASE_URL`/`DATABASE_URL`. `post { always { docker compose -p ... down } }` tears down that build's own throwaway DB whether the stage passes or fails, without touching any other build's — including two builds of the *same* job, since `BUILD_TAG` carries `BUILD_NUMBER`. Ungated by branch, like Test — PRs get the same regression coverage as pushes to main. The port resolution is guarded explicitly (`docker compose port | awk ...` has no `pipefail`, so a failed lookup would otherwise leave `TEST_DB_PORT` empty and `pg.Client` would silently default to port 5432 — this host's production `cistory-db`); an empty result fails the stage immediately instead. Note `options { disableConcurrentBuilds() }` on the pipeline exists for a *different* reason than this stage — see its comment in the Jenkinsfile: it serializes the deploy path (Run Migrations/Deploy/Cleanup, which still hardcode `cistory-db` and `:latest`), not the integration database, which doesn't need it.
- **Docker** (`Dockerfile`): multi-stage on Node 24.22.2 Alpine (browser tests use Debian) — `base → deps → builder → tester → browser-tester → integration-tester → migrator → runner`. `.env` mounted as a build secret; only `NEXT_PUBLIC_*` vars are extracted for the build. Runs as non-root `nextjs` (UID 1001), using `output: "standalone"` from `next.config.ts`. The `deps` and `browser-tester` stages `COPY .yarn/patches` before `yarn install --immutable` (Proton crypto patch); the standalone trace includes the tfjs wasm binaries via `outputFileTracingIncludes`
- **Web/cron container split**: the same image runs twice — web (`cistory`, port 3000, `DISABLE_CRON=true`) and cron (`cistory-cron`, no published port). Jenkins stops/removes both on each deploy
- **Docker Compose**: `cistory` + `cistory-cron` + `postgis/postgis:17-3.7-alpine` with external volume `cistory_postgres_data`
- **Timezone**: production containers run with `TZ=Asia/Seoul` (KST, UTC+9)
- Jenkins cleanup keeps only the last 3 image tags

## Code Style

- **Biome** for linting/formatting (`biome.json`); auto-organizes imports
- Formatting: 2-space indent, double quotes, semicolons, trailing commas (ES5), 100 char line width
- Lint: unused imports are errors, unused variables are warnings, `useImportType` enforced, `noNonNullAssertion` off, `noExplicitAny` warn, `noExcessiveCognitiveComplexity` warn, `useExhaustiveDependencies` warn
- Naming: PascalCase React components (`DayMap.tsx`), `useCamelCase` hooks, camelCase functions/variables, Next.js `page.tsx`/`route.ts`
- Path alias: `@/*` maps to `./src/*`
- Prefer Drizzle ORM query builder (avoid raw SQL); keep feature logic in its module and shared infrastructure in `src/lib`
- Follow Next.js App Router conventions (Server Components by default)
- Korean language used for user-facing strings in API responses and UI
- Commits follow Conventional Commit subjects (`feat:`, `fix:`, `test:`, `perf:`, `docs:`, and scoped forms like `fix(security):`). Run `yarn test`, `yarn lint`, and `yarn build` before opening a PR; update `.env.example` when introducing configuration
- **Date parsing**: Never use `new Date("YYYY-MM-DD")` for date-only strings — ECMAScript parses this as UTC midnight, so "2026-03-04" becomes March 3rd 15:00 KST. Canonical helpers in `src/lib/utils.ts`: `parseDateLocal()`, `toLocalDateString()`, `startOfLocalDay()`/`endOfLocalDay()`, `parseDateParam()`. Never derive a date key with `date.toISOString().split("T")[0]` — that is the UTC day, which shifts 00:00–09:00 KST activity onto the previous day; use `toLocalDateString()`
- **Timestamps in SQL**: `timestamp` (without time zone) columns store **UTC wall time** (Drizzle serializes via toISOString on write). Deriving a KST calendar day in SQL therefore requires `(col AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Seoul')::date` — helpers in `src/db/sql.ts` (`localDaySql`, `localDayRawSql`). Both `DATE(col)` and `col AT TIME ZONE 'Asia/Seoul'` are wrong (they yield the UTC day)
- **…but `now()` does NOT follow that convention.** In raw `sql`, a bare `now()` (and any DB `DEFAULT now()`) is cast timestamptz→timestamp using the **session** timezone, and this server's default is `Asia/Seoul` (`pg_settings.source = 'configuration file'`; the pool sets no timezone). Such a value lands as **KST wall time**, 9 hours off from everything Drizzle writes. Two columns written by one operation can therefore sit exactly 9h apart and both be correct — check `information_schema.columns.column_default` before calling such a gap a bug. In raw writes bind a JS Date via `timestampParam(column, date)` and read raw results back through `timestampFromDriver` (both in `src/db/sql.ts`, added by `7790bb5`/`671aa1a` after this bit the overview module; the health rollup was fixed the same way). The ~23 columns still carrying `DEFAULT now()` remain on the KST convention — nothing reads them, and changing them needs a backfill
