# Cistory 서비스 진단

Cistory는 GitHub·WakaTime·OwnTracks·Toss·KIS·Withings·Google Health/Health Connect를 모아 하루 타임라인, 여행, 기간별 회고를 만드는 개인 생활기록 서비스다. 연결하는 소스와 분석 기능은 이미 충분히 넓다. 다음 개선의 중심은 기록의 정확성, 누락 복구, 다시 찾기, 사용자 맥락 보존이다.

## 검토 범위와 확인 결과

- 현재 체크아웃의 애플리케이션 코드, 스키마, 배포 설정, 기존 설계 문서를 검토했다. 특정 PR 변경분 검토가 아니다.
- Node 22로 `yarn test`: 107개 파일, 990개 테스트 통과.
- Node 22로 `yarn exec tsc --noEmit --incremental false`: 통과.
- Node 22로 `yarn lint`: 종료 성공, 경고 95개와 정보 1개. 자동 수정하지 않았다.
- `yarn npm audit --all --recursive --json`: 35개 결과 행. 중복 버전과 사용 중단 안내를 제외하면 고유 보안 권고 URL은 29개다. 이는 서비스에서 악용 가능한 취약점 29개를 입증한 결과가 아니다.
- 운영 DB, 외부 계정의 실제 기록, 인증된 브라우저 화면은 사용하지 않았다. 빌드와 Docker 통합 테스트는 이번 검토에서 실행하지 않았다.
- 건강 연관성 문구는 현재 함수의 코드를 추출해 반례 입력으로 실행했다. 수익률은 독립 검증에서 실제 `computeReturns` 함수로 재현했다. 나머지는 코드 경로 확인에 근거한다.
- 애플리케이션 코드를 수정하지 않았다. 기존 AGENTS.md 수정은 사용자 변경으로 보존했다.

| Node.js | 프로젝트/배포 22, 이번 기본 셸 26.0.0 | 24 LTS | 우선 로컬·CI·Docker·타입 버전을 일치시킨다. 24는 지원 수명 확보를 위한 별도 변경으로 검증한다. 22는 아직 지원 중이다. |

추가 우선순위:

1. **간접 의존성 패치.** 선언 버전을 올리는 것만으로 lockfile에 남은 취약 버전이 없어지지 않는다. 이번 audit에서 defu 6.1.4는 Better Auth 아래, tar 7.5.7은 node-gyp 아래에서 발견됐다. defu 패치는 6.1.5다. 실제 호출 경로를 확인해 런타임과 빌드 도구 위험을 나누고 호환 가능한 lockfile 갱신부터 한다. critical 표시 하나가 운영 HTTP 경로 악용을 입증하지는 않는다.
2. **TanStack Query 점진 도입.** 타임라인 거래, 건강 보조 카드 등 단순 조회부터 캐시 키/신선도/재검증/오류를 통일한다. 현재 수동 useEffect+Map 구현의 정확성 문제를 줄이는 목적이다. 개선 지표는 중복 요청 수와 변경 후 화면 반영 시간이다. SSE/지도 재생/모든 UI 상태를 한꺼번에 옮기지 않는다.
3. **백그라운드 작업의 원자적 소유권.** 커밋 요약은 대기 목록 SELECT 이후 상태를 무조건 UPDATE하므로 수동 API와 cron이 같은 작업을 읽을 수 있다. 이미 overview에 있는 PostgreSQL claim/lease 패턴을 우선 재사용한다. 인메모리 import job은 재시작 시 사라지는 의도된 제약이므로 대형 임포트 빈도가 높아질 때 영속 체크포인트를 추가한다.
4. **작은 브라우저 회귀 검증.** Jenkins의 단위/DB 통합 검증은 이미 있다. 추가할 부분은 차트가 실제로 보이는지, 빈 화면·실패·날짜 전환이 맞는지다. 기존 문서가 UI 테스트를 의도적으로 제외했음을 고려해 핵심 화면 몇 개부터 시작한다.
5. **쿼리는 측정 후 변경.** `/api/summaries/process` GET은 사용자 커밋 ID 전량을 가져온 뒤 IN 조건으로 다시 집계한다. JOIN + GROUP BY로 바꾸면 ID 전량 전송과 큰 바인드 목록을 피할 수 있다. 실제 사용자 기록량에서 쿼리 지연과 요청 메모리를 비교한다.
6. **README를 실제 운영 진입점으로 교체.** 현재 create-next-app 기본 문서다. 연동 순서, 필수 환경변수 이름, 최소 실행 모드, 백업·복구 절차를 제공하면 긴 내부 설명 없이도 서비스를 시작하고 복구할 수 있다.

기존 결정도 유지할 가치가 있다. Mapbox는 이미 지연 로딩하고, overview는 사전 집계하며, cron은 별도 컨테이너다. AI Batches와 프롬프트 캐싱은 기존 실측에서 월 약 $5 사용량 및 짧거나 달라지는 프리픽스 때문에 기각했다. 새로운 비용 측정 없이 이를 다시 최우선 과제로 제안하지 않는다.

## 기능 제안의 기준

코드에서 확인한 기존 기능을 출발점으로 12개 후보를 먼저 만들고, 중복 기능·새 연동의 유지비·개인 서비스 적합성을 검토했다. 아래 신뢰도는 제품 효과에 대한 주관적 판단이며 실제 사용자 실험 확률이 아니다.

검토 축은 네 가지다: 수집의 신뢰성, 기록을 다시 찾는 경험, 사용자가 의미를 붙이는 경험, 장기 보관과 통제.

## 추천 기능

### 1. 수집 공백을 보여주는 데이터 상태 화면

- **내용:** 소스별 마지막 성공, 실제 기록이 존재하는 날짜, 누락 의심 구간, 해당 구간 재수집을 한곳에 보여준다. 0건과 수집 실패를 구분한다.
- **근거:** `reasoned:` 여러 소스의 수집 주기와 복구 방법이 다르다. `AsOfBadge`는 집계 시각을 보여주며 소스별 원본 완전성을 뜻하지 않는다. 일부 설정 카드의 재연동/동기화 기능을 통합하는 제안이다.
- **효과:** 사용자가 기록의 진위를 먼저 판단할 수 있다. 자료가 없는 날을 소비·활동 0으로 오해하는 일을 줄인다.
- **첫 범위:** 연결된 소스 목록과 마지막 성공/실패, 하루 단위 누락 표시. 기록이 원래 없는 날을 장애로 단정하지 않는다.
- **지표:** 수집 실패를 발견하고 복구하기까지 걸린 시간, 설명되지 않는 공백 날짜 수.
- **부담:** 소스별 정상 수집 주기가 달라 공통 상태 모델이 필요하다.
- **축:** 수집의 신뢰성. **신뢰도:** 90%. **복잡도:** Medium.

### 2. 근거 기록으로 연결되는 통합 기억 검색

- **내용:** 날짜·장소·가맹점·저장소·여행 이름을 함께 검색하고 해당 날짜 타임라인, 여행, 커밋으로 이동한다. 예: “지난 부산 여행 중 카페에 있던 날의 작업”.
- **근거:** `reasoned:` 데이터는 동일 사용자·시간을 중심으로 연결될 수 있지만 조회 UI는 개별 도메인으로 나뉘어 있다. 지도 검색은 장소 찾기이며 전체 개인 기록 검색과 다르다.
- **효과:** 보고서를 읽는 서비스에 지난 일을 찾아 쓰는 목적을 더한다.
- **첫 범위:** 날짜/키워드/소스 필터 검색. 자연어 변환은 나중에 붙여도 된다. 사람 검색은 사람을 기록하는 데이터가 확보된 뒤 다룬다.
- **지표:** 찾으려던 기록까지 걸린 시간, 검색 후 근거 기록을 연 비율.
- **부담:** 다른 소스의 시간대·동일 장소 매칭 품질이 검색 결과에 영향을 준다.
- **축:** 기록을 다시 찾는 경험. **신뢰도:** 85%. **복잡도:** Medium.

### 3. 재탐지해도 보존되는 여행 보정과 메모

- **내용:** 자동 여행의 이름·기간을 고치고 한 줄 메모를 붙인다. 수정 내용은 자동 탐지 결과와 구분해 보존한다.
- **근거:** `direct:` `src/app/api/trips/[id]/route.ts`는 “PUT /api/trips/:id — Update trip”을 제공하지만 상세 화면에는 메모 표시/편집이 없고, B8의 재탐지 손실 가능성이 있다.
- **효과:** 자동 기록의 잘못된 경계를 바로잡고, 좌표가 설명하지 못하는 개인 기억을 남긴다.
- **첫 범위:** 이름과 메모 표시/수정 및 재탐지 후 보존. 여행 병합·분할은 다음 범위다.
- **지표:** 보정 후 다시 틀어진 여행 수, 메모 보존 실패 수.
- **부담:** 자동 여행 ID 재생성과 사용자 필드 보존 정책을 먼저 해결해야 한다.
- **축:** 사용자가 의미를 붙이는 경험. **신뢰도:** 90%. **복잡도:** Medium.

### 4. 회고에 사용자 맥락과 다음 행동 남기기

- **내용:** 기존 주간·월간 AI 회고에서 중요한 부분을 저장하고 “출장 때문에 수면이 줄었다” 같은 맥락을 추가한다. 선택적으로 다음 주에 확인할 한 가지 변화를 기록한다.
- **근거:** `reasoned:` 기간 회고는 이미 구현되어 있다. 자동 센서와 거래 데이터만으로는 어떤 변화가 의도된 것인지 알 수 없으므로 사용자 설명이 회고의 해석을 보완한다.
- **효과:** 일회성 생성문을 다음 회고에서 다시 꺼내는 개인 기록으로 만든다.
- **첫 범위:** 회고에 연결된 한 줄 메모와 북마크. AI 원문과 사용자 글을 구분한다.
- **지표:** 지난 회고 재열람 비율, 저장한 맥락을 후속 회고에서 활용한 횟수.
- **부담:** 입력 부담을 늘릴 수 있다. 매일 작성 강제나 습관 점수는 필요하지 않다.
- **축:** 사용자가 의미를 붙이는 경험. **신뢰도:** 75%. **복잡도:** Medium.

### 5. 개인 기록 내보내기와 선택적 정리

- **내용:** 기간·소스를 선택해 거래 CSV, 위치 GeoJSON, 통합 JSON과 보정 메모를 내려받는다. 소스별 기록 삭제는 내보내기와 별개로 명확하게 제공한다.
- **근거:** `reasoned:` 수집·임포트·소스별 연결 해제는 있지만 통합 내보내기 UI/API는 확인하지 못했다. 오래 쌓인 개인 기록의 가치는 서비스 구현보다 오래 유지되어야 한다.
- **효과:** 기록의 장기 활용과 다른 도구로의 이동을 가능하게 한다.
- **첫 범위:** 한 달·한 소스 다운로드부터 시작하고, 형식 버전과 시간대 정보를 포함한다.
- **지표:** 샘플 내보내기와 재읽기에서 보존되는 레코드/필드 비율, 내보내기 완료율.
- **부담:** 대형 파일 처리, 민감 파일 보관, 복원 형식의 호환성 유지가 필요하다. export가 운영 DB 백업을 대체하지는 않는다.
- **축:** 장기 보관과 통제. **신뢰도:** 85%. **복잡도:** Medium.
